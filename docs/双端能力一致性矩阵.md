# HiddenShield 双端能力一致性矩阵

本文档对应 `docs/双端能力一致性Roadmap.md` 的 Phase A，用于把桌面端与移动端当前能力差距固化为后续执行依据。

审计范围：

- 图片写入、提取、验证、重写与完成态。
- 音频写入、提取、格式处理、30 秒规则与完成态。
- 版权库字段、正式报告字段、云同步字段。
- 本地批量、L2 视频指纹存证与允许的平台差异。

## 1. 优先级定义

| 优先级 | 定义 | 处理原则 |
| --- | --- | --- |
| P0 | 会造成用户误解、能力缺失、验证结果不一致或破坏产品承诺 | 进入下一阶段优先修复 |
| P1 | 能力主体可用，但字段、文案、报告或体验不完整 | 紧随 P0 修复，避免形成长期债务 |
| P2 | 体验优化、命名清理、自动化覆盖增强 | 在 P0 / P1 收敛后推进 |

## 2. 总览结论

| 领域 | 桌面端现状 | 移动端现状 | 一致性结论 | 优先级 | 建议动作 |
| --- | --- | --- | --- | --- | --- |
| 图片写入 | 支持 jpg / jpeg / png / bmp / tiff / webp / gif 归类为图片，保护副本以 PNG 为主 | 通过系统图片选择器导入，Rust 桥接输出 PNG | 主能力基本一致，格式边界需要产品化说明 | P1 | Phase B 对齐支持格式说明、输出格式说明和失败态 |
| 图片验证 | 桌面端输出 `VerificationResult`，包含置信度、本地记录匹配、原因码、TSA、原始哈希 | 移动端可读水印并入库取证，但结果模型较轻 | 移动端验证结果不够接近桌面端 | P0 | 抽象移动端验证结果模型，补齐本地版权库匹配、置信度和原因码 |
| 图片重写 | 桌面端根据父记录计算 revision，并保留 parent / rewrite reason | 移动端写入页也有“作为新版写入”和 preflight | 主流程一致 | P1 | Phase B 做双端文案和结果卡微对齐 |
| 音频写入格式 | 桌面端支持 wav / mp3 / flac / aac / ogg / m4a，FFmpeg 转 WAV 后写入 | 移动端支持 wav / mp3 / aac / flac / ogg / m4a，Symphonia 解码后写 WAV | 格式列表一致，但转换策略不同 | P0 | Phase C 明确并统一“保留声道 / 采样率”的技术策略 |
| 音频 30 秒规则 | 桌面端依赖 FFprobe / pipeline 元数据判断更可靠 | 移动端页面只用 WAV header 解析时长，非 WAV 时长为 null | 非 WAV 短音频可能绕过 30 秒预检 | P0 | 移动端用 Rust/Symphonia 或统一 metadata API 返回非 WAV 时长 |
| 音频声道与采样率 | 桌面端 `extract_audio` 当前强制 `44100Hz + 2ch` | 移动端非 WAV 解码保留源采样率和声道数，再写成 16-bit WAV | 与“不能破坏源文件属性”的原则不一致 | P0 | 桌面端改为保留源声道和采样率，至少保留单声道 / 双声道 |
| 音频验证 | 桌面端验证会匹配本地版权库并给出原因码、置信度和报告信息 | 移动端直接读取水印并保存取证记录 | 用户看到的取证结论不一致 | P0 | 移动端复用桌面验证语义：有效水印、命中本地记录、疑似水印、未命中 |
| 版权库字段 | 桌面端记录包含原始哈希、输出哈希、TSA、AI 内容、L2 元数据等 | 移动端 `VaultRecord` 已覆盖 revision、parent、验证状态、同步状态、L2 元数据 | 主字段已接近，但桌面端 TSA / 输出平台哈希 / AI 字段移动端展示不足 | P1 | Phase D 对齐详情页字段分组和同步字段白名单 |
| 正式报告 | 桌面端导出 JSON + Markdown，包含隐私边界、可信时间、AI 字段、L2 bundle 元数据 | 移动端生成 Markdown 草案，已包含隐私边界、版本、验证、L2 字段 | 移动端没有桌面端同等的结构化 JSON 与可信时间字段 | P1 | Phase D 对齐报告 schema 和字段显示，不引入媒体或本地路径 |
| 云同步 | 桌面端上报版权记录、创作者档案、权益、L2 存证字段；排除原始媒体和本地路径 | 移动端有云同步 profile、队列、重试、冲突解决和字段 payload | 主模型基本一致 | P1 | Phase F 建立双端同步字段合同，防止字段漂移 |
| 本地批量 | 桌面端已有批量队列和 Creator 门禁 | 移动端已有本地批量页面和队列模型 | 能力方向一致，实际处理能力需继续验收 | P1 | Phase E 对齐失败重试、暂停继续取消和完成后验证态 |
| L2 视频存证 | 桌面端生成和提交 VideoFingerprintBundle | 移动端只展示同步来的 L2 存证记录和报告字段 | 这是允许差异：移动端不做本地视频盲水印 | P1 | Phase G 保持“只读展示 + 报告一致”，禁止暗示本地视频水印 |
| 技术语言 | 桌面端较少暴露桥接概念 | 移动端桥接文案已大幅隐藏，但代码命名仍有 `AudioWavForMobile` | 用户侧基本可控，开发侧命名存在误导 | P2 | 后续统一桥接命名为 audio / image，不再强调 WAV |

## 3. P0 详细差距

### 3.1 移动端非 WAV 音频 30 秒预检不完整

证据：

- `mobile_app/lib/features/workspace/audio_embed_page.dart` 允许 `wav/mp3/aac/flac/ogg/m4a`。
- 当前 `_wavDurationSeconds` 只解析 RIFF / WAVE header。
- 非 WAV 文件会得到 `null` 时长，页面只在 `durationSeconds != null && durationSeconds < 30` 时阻止写入。

影响：

- 10 秒 MP3 / AAC / FLAC 等短音频可能不会在页面预检阶段被拦住。
- 与“30 秒以上音频才进行版权保护”的产品口径冲突。

建议：

- 移动端新增统一音频 metadata API，由 Rust/Symphonia 返回 `durationSeconds`、`sampleRate`、`channels`、`codec/container`。
- 页面只允许 `durationSeconds >= 30` 进入写入。
- metadata 不可读时，不进入写入，给出“无法确认音频时长，请更换完整音频文件”的明确提示。

### 3.2 桌面端音频转换强制 44.1kHz 双声道

证据：

- `src-tauri/src/pipeline/scheduler.rs` 的 `extract_audio` 使用 FFmpeg 参数 `-ar 44100` 和 `-ac 2`。
- 移动端 `mobile_app/rust/src/api.rs` 的非 WAV 解码会保留源 `sample_rate` 和 `channels` 后写成 WAV。

影响：

- 桌面端与移动端对同一音频可能生成不同中间 WAV。
- 与“原音频是双声道就继续双声道，单声道就继续单声道，不能破坏源文件”的产品原则冲突。

建议：

- 桌面端先通过 FFprobe 读取源音频 `sample_rate` 和 `channels`。
- FFmpeg 转 WAV 时保留源采样率和声道；只在异常或不支持时走受控降级。
- 降级必须写入验证消息和报告字段，用户可见但不技术化。

### 3.3 移动端验证结果模型弱于桌面端

证据：

- 桌面端 `verify_suspect` 输出 `matched`、`watermarkUid`、`confidence`、`matchedRecord`、`reasonCode`、`reasonDetail`、TSA 状态、原始哈希。
- 移动端 `VerifyPage` 直接调用 bridge read，成功后 `addReadResult`，失败时用 `MobileVerifyReason` 做轻量说明。

影响：

- 同一个样本在桌面端可能显示“命中本地版权库 / 疑似修改 / 未同步记录”，移动端只显示“读到了水印”。
- 版权取证和正式报告的可信度表达不一致。

建议：

- 移动端新增 `MobileVerificationResult`，字段与桌面端 `VerificationResult` 对齐。
- 成功读取水印后先匹配本地版权库：UID + file hash prefix + revision。
- 对齐原因码：`matched_original`、`matched_output`、`matched_hash_mismatch`、`watermark_detected_unregistered`、`low_confidence`、`no_valid_watermark`。

## 4. P1 详细差距

### 4.1 图片格式和输出格式需要统一口径

桌面端会把 jpg / jpeg 映射为 PNG 输出，png 输出 PNG，webp / bmp / tiff 有格式映射；移动端当前统一输出 PNG。核心能力可接受，但产品文案必须统一为“生成保护副本”，不要暗示保留原扩展名。

建议 Phase B 统一：

- 导入格式列表。
- 输出保护副本格式说明。
- 写入完成态中的“保护副本可取证”文案。
- 裁剪、缩放、亮度、噪声、90 / 180 / 270 / 镜像的能力边界。

### 4.2 版权库详情字段接近，但展示层仍需对齐

移动端 `VaultRecord` 已包含：

- `watermarkUid`、`revision`、`parentWatermarkUid`、`rewriteReason`。
- `writeVerificationStatus`、`writeVerificationMessage`、`writeVerificationAt`。
- `videoNotaryId`、`videoFingerprintRoot`、`videoBundleSha256`、`videoBundleBytes`、`videoBundleSceneCount`、`videoBundleElapsedMs`、`videoFrameSamplePolicy`。

桌面端额外强调：

- 输出平台哈希。
- TSA token / network time / TSA source。
- AI 内容声明字段。

建议 Phase D 对齐详情页字段：

- 基础版权信息。
- 写入后验证信息。
- 可信时间与 TSA。
- L2 视频指纹存证。
- 隐私边界：不同步原始媒体、加水印媒体、本地路径。

### 4.3 正式报告字段应统一 schema

桌面端正式报告包含结构化 JSON 和 Markdown；移动端当前是 Markdown 草案。两端都已经包含“不包含原始媒体 / 不包含加水印媒体 / 不包含本地路径”和“报告不是法律意见”的口径。

建议 Phase D：

- 提取共享报告字段清单。
- 移动端报告草案补齐可信时间字段。
- 桌面端与移动端统一 L2 字段命名：存证编号、存证时间、收据签名、用量流水、指纹根、指纹包摘要、指纹包大小、采样帧、生成耗时、采样策略。

### 4.4 云同步需要合同化

双端同步模型已经围绕版权记录、创作者身份、权益、队列和冲突处理展开，且都遵守“不上传原始媒体 / 不上传加水印媒体 / 不上传本地路径”。

建议 Phase F / H：

- 建立 `dual:contract`。
- 校验桌面端 `vault_record_to_cloud_event` 与移动端 `VaultRecord.toSyncPayload()` 的字段一致性。
- 校验字段白名单中不出现 `localPath`、`originalMedia`、`watermarkedMedia`、本地 bundle 路径。

## 5. 允许差异

| 差异 | 结论 | 用户可见口径 |
| --- | --- | --- |
| 移动端不做本地视频盲水印写入 | 允许 | 移动端只展示 L2 视频指纹存证记录，不提供本地视频水印入口 |
| 桌面端生成 L2 视频指纹包，移动端只读展示 | 允许 | L2 是视频指纹存证，不是视频画面盲水印 |
| 双端不同步原始媒体、加水印媒体、本地路径 | 必须保持 | 同步只包含版权记录、创作者身份、权益、验证和存证元数据 |
| 移动端可能受系统文件选择器限制 | 允许 | 只承诺当前页面列出的可选格式，失败时给出非技术化提示 |

## 6. 下一阶段修复顺序

1. Phase C：先修音频一致性。
   - 移动端补齐非 WAV 时长预检。
   - 桌面端音频转换改为保留源声道和采样率。
   - 双端验证错误码和失败文案对齐。

2. Phase B：再修图片验证一致性。
   - 移动端验证结果模型补齐本地版权库匹配和原因码。
   - 双端图片完成态、版本态和攻击边界文案统一。

3. Phase D：补齐版权库与正式报告。
   - 对齐详情页字段。
   - 对齐正式报告 schema。
   - 确认隐私边界字段不回退。

4. Phase H：最后固化合同。
   - 新增 `dual:contract`。
   - 接入 CI，避免后续桌面端、移动端、云端任意一侧改接口时破坏一致性。

## 7. 阶段结论

当前双端已经具备同一产品的基础形态：图片 / 音频写入、验证、版权库、同步、报告、L2 展示均有实现基础。

但还不能称为“能力完全一致”。最需要马上处理的是音频：

- 移动端非 WAV 30 秒规则存在预检缺口。
- 桌面端音频中间转换会强制双声道和 44.1kHz。
- 移动端验证结果没有桌面端的本地记录匹配和原因码深度。

因此下一阶段应优先进入 Phase C，而不是继续商业化页面或 L2 扩展。
