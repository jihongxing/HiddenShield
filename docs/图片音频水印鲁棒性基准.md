# 图片音频水印鲁棒性基准

这个基准用于评估图片/音频写入后的可验证性，重点观察水印在常见二次处理后的提取稳定性。

音频写入基准默认使用 30 秒样本。短于 30 秒的音频不作为 HiddenShield 音频版权保护的产品承诺范围；短裁剪片段只作为取证扩展观察项。

## 性能口径

- `watermark:bench` 默认使用当前构建模式运行，适合看稳定性和回归。
- `cargo run --release --bin robustness_bench` 用于记录正式性能基线。
- 报告中的 `Write ms` 只统计 `WatermarkService::embed(...)` 本体。
- 报告中的 `Read ms` 只统计 `WatermarkService::extract(...)` 本体。
- `ffmpeg` 转码、裁剪和文件读写不计入上述两项。

## 发布门禁口径

发布前先生成图片和音频 release 报告，再用 `watermark:release-gate` 读取 `report.json` 做判定：

```powershell
npm run watermark:bench:release -- --image-dir "E:\Users\jihx\Pictures\人脸" --max-images 17 --max-audio 0 --output-dir watermark-core/target/robustness-bench-image-release
npm run watermark:bench:release -- --audio-glob "E:\Users\jihx\Pictures\*.mp3" --max-images 0 --max-audio 9 --output-dir watermark-core/target/robustness-bench-audio-release
npm run watermark:release-gate -- watermark-core/target/robustness-bench-image-release/<run-dir>/report.json watermark-core/target/robustness-bench-audio-release/<run-dir>/report.json
```

门禁规则：

- 图片生产结果必须全部通过。
- 音频生产结果只统计 30 秒以上作品的常规场景，必须全部通过。
- `clip_10s_middle` 和 `matrix_*` 属于短裁剪观察项，会在门禁输出中展示，但不阻断发布。
- 新增音频 transform 必须先归类为生产项或观察项，不能默认混入 release 判断。

## 运行方式

```powershell
npm run watermark:bench -- --image-dir "E:\Users\jihx\Pictures\人脸" --audio-glob "E:\Users\jihx\Pictures\*.mp3"
```

默认只取前 3 张图片和前 3 个音频，输出目录为：

```text
watermark-core/target/robustness-bench/run-<timestamp>/
```

其中：

- `report.md`：人工阅读报告
- `report.json`：后续自动化分析用报告
- `images/`：每个图片样本的写入结果和变换结果
- `audio/`：每个音频样本的 WAV 中间文件和变换结果

## 覆盖场景

图片：

- 基线 PNG
- PNG 重新编码
- JPEG 90 质量
- JPEG 75 质量
- 缩放到 85%
- 亮度 90% / 110%
- 1% 椒盐噪点
- 15% 中心遮盖
- 15% 横向 / 纵向切割
- 90 / 180 / 270 度旋转
- 水平 / 垂直镜像
- 2% 轻裁剪
- 版权库参考辅助 2% 轻裁剪，作为深度检测指标，不计入默认盲检测承诺

音频：

- 基线 WAV
- WAV 重新编码
- 音量 80%
- 音量 120%
- 重采样到 22050 Hz
- MP3 192k 转码后再转回 WAV


### 音频 release 基线

最近一轮 9 首真实音频样本的 release 基线结果。音频生产口径只统计 30 秒以上作品的常规写入/验证场景；`clip_10s_middle` 是 10 秒短裁剪取证观察项，不计入生产通过率：

```powershell
npm run watermark:bench:release -- --audio-glob "E:\Users\jihx\Pictures\*.mp3" --max-images 0 --max-audio 9 --output-dir watermark-core/target/robustness-bench-audio-release
npm run watermark:release-gate -- watermark-core/target/robustness-bench-image-sync-correction/run-1781775861/report.json watermark-core/target/robustness-bench-audio-release/run-1781780559/report.json
```

报告目录：

```text
watermark-core/target/robustness-bench-audio-release/run-1781780559/
```

| 指标 | 结果 |
| --- | ---: |
| 音频样本数 | 9 |
| 生产口径总结果 | 54/54 passed |
| 常规场景数 | 9 首 x 6 场景 |
| 写入耗时均值 | 306.8 ms/首 |
| 写入耗时范围 | 281~333 ms/首 |

常规 6 个场景包括基线 WAV、WAV 重新编码、音量 80%、音量 120%、重采样到 22050 Hz、MP3 192k 转码后再转回 WAV。原始混合口径的 6 个失败项全部来自 `clip_10s_middle`，因此不能用 `57/63` 判断 30 秒以上音频的常规生产能力失败。

样本的时长、码率、采样率、声道和响度已写入 `report.json`，可继续按风格分组做后续分析。

### 10 秒裁剪诊断

对 6 首真实音频的 `clip_10s_middle` 做了进一步诊断：

- `embedded_30s` 全部稳定恢复，最佳 packet errors 为 0。
- `clip_10s_middle` 失败样本大多 `marker_hits = 0`，说明短裁剪已经丢失足够的定位证据。
- 失败样本的最佳 packet errors 主要落在 `13~27`，问题集中在 preamble 和 payload，不是 checksum。
- 能通过的短裁剪样本，通常仍保留少量 marker 命中，且 packet errors 明显更低。

结论：

- 当前短裁剪失败更像是“局部同步和证据密度不足”。
- 10 秒短裁剪不属于当前生产承诺，不能混入音频 release 生产通过率。
- 继续扩大提取端猜测范围的收益有限；后续音频优化应优先服务 30 秒以上作品的写入稳定性、写入后验证和常规二次处理鲁棒性。

## 参数

```powershell
npm run watermark:bench -- `
  --image-dir "E:\Users\jihx\Pictures\人脸" `
  --audio-glob "E:\Users\jihx\Pictures\*.mp3" `
  --max-images 10 `
  --max-audio 10
```

可选参数：

- `--max-images <N>`：限制图片样本数
- `--max-audio <N>`：限制音频样本数
- `--output-dir <dir>`：自定义报告输出目录
- `--ffmpeg <path>`：指定 FFmpeg 路径

## 判定规则

每个变换都会重新提取水印，并与写入时的 `watermark_uid` 对比：

- `PASS`：能提取，且 UID 一致
- `FAIL`：提取失败，或提取出的 UID 与期望不一致

这个工具只读取原始素材，不会覆盖素材目录里的文件。
