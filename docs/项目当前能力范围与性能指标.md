# HiddenShield 项目当前能力范围与性能指标

更新时间：2026-07-31

## 1. 文档定位

本文回答四个问题：

1. HiddenShield 当前可以对用户承诺哪些媒体保护能力。
2. 支持哪些输入类型，以及素材尺寸、时长和文件大小范围。
3. 在已有测试样本上，写入和读取分别需要多长时间。
4. 哪些数据只是内部实验、历史基线或北极星目标，不能作为当前 SLA。

当前正式口径以 Windows 桌面发布版 `v0.1.3` 为主。移动端、视频画面水印、生产云 SDK/API、公共 Resolver、真实支付和公共信任层不纳入当前用户承诺。

## 2. 一页结论

| 媒体 | 当前状态 | 正式输入 | 正式输出 | 当前范围 |
| --- | --- | --- | --- | --- |
| 静态图片 | 可对用户承诺 | PNG、JPEG/JPG、WebP | 同像素尺寸 PNG | 容量预检通过至 100 MP；文件不超过 512 MiB |
| 音频 | 可对用户承诺 | WAV、MP3、FLAC、OGG、M4A | WAV | 30 秒至 20 分钟；不超过 512 MiB；8–48 kHz；单/双声道 |
| 视频音轨水印 | 内部保留，当前隐藏 | 不对用户开放 | 不对用户开放 | 历史实现复用音频核心，但不进入当前 UI、报告或权益 |
| 视频画面水印 | 只能内部测试 | 受控测试样本 | 受控测试产物 | L3 release candidate 与 worker 闭环不等于当前产品能力 |
| 移动端图片/音频正式发布 | 当前冻结 | 不作正式发布承诺 | 不作正式发布承诺 | Rust bridge 与跨端合同存在，但不能外推桌面发布状态 |
| 云 SDK/API、公共 Resolver | 只能内部测试 | 受控 PNG/记录查询流程 | 内部 QA 结果 | 尚未开放生产凭据、公网服务、SLA 或客户下载 |

## 3. 正式能力范围

### 3.1 静态图片

#### 支持类型

- 输入：静态 PNG、JPEG/JPG、WebP。
- 输出：PNG 保护副本。
- 输出保持源图片像素宽高不变。
- 正式载荷：V3/39。
- 写入后必须回读同一 `watermarkUid`，并通过 payload 认证。

#### 素材范围

| 指标 | 当前正式边界 |
| --- | --- |
| 最小宽高 | 不设固定宽高；由 `watermark-core` 分块容量预检决定 |
| 已知失败参考 | 320×240 的 PNG/JPEG/WebP 基线样本不能稳定完成保护，不应作为最低支持规格 |
| 常规实测规模 | 2–4 MP |
| 大图实测规模 | 4096×2160 及约 99.92 MP |
| 最大像素数 | 100 MP |
| 最大源文件大小 | 512 MiB |
| 超限行为 | `100 MP + 1 pixel` 或 `512 MiB + 1 byte` 拒绝，不创建正式记录 |
| 资源提示 | 50–100 MP 显示高资源警告，建议至少 16 GiB 内存 |

“不设固定最小宽高”不等于任意小图都支持。产品应显示“容量不足”而不是宣称一个未经大样本验证的最小分辨率。

#### 已验证的独立变换恢复

- 轴对齐裁切：裁切结果宽、高分别至少为原图的 `1/4`。
- 旋转：90°、180°、270°。
- 缩放：85%。
- JPEG 重编码：quality 75、60。
- WebP 重编码：quality 75、60。

这些是单项变换承诺，不能组合外推。当前不承诺任意角度旋转、低于 80% 缩放、低于 quality 60、多个扰动叠加、动画逐帧语义或遮挡后的同等恢复率。

### 3.2 音频

#### 支持类型

- 输入：WAV、MP3、FLAC、OGG、M4A。
- 输出：WAV 保护副本。
- 保护副本保持源采样率和单/双声道布局。
- 支持的 WAV PCM 路径包括 16/24/32-bit integer 和 32-bit float；64-bit float 明确拒绝。
- 有损输入解码后不承诺保留原容器或原编码格式。

#### 素材范围

| 指标 | 当前正式边界 |
| --- | --- |
| 最短时长 | 30 秒 |
| 最长时长 | 20 分钟 |
| 最大源文件大小 | 512 MiB |
| 采样率 | 8–48 kHz |
| 声道 | mono / stereo |
| 超限行为 | 超过时长、文件大小、采样率或声道范围时拒绝，不允许通过端侧静默重采样或降声道规避 |

当前已验证五种输入格式 × mono/stereo 共 `10/10` 的安装版写后回读、独立核心读取和只读验证。`20 分钟 / 48 kHz / stereo / 24-bit FLAC` 上包络也已完成安装版验证。

#### 后处理边界

当前正式客户口径只承诺支持规格内、未继续编辑的 WAV 保护副本读取。以下结果虽有内部或历史基准证据，但不应写入当前稳定客户承诺：

- WAV 重新编码。
- 音量调整。
- 重采样。
- MP3 往返转码。
- 裁剪、拼接、变速、变调、EQ、降噪、混音和加噪。

其中 5–15 秒短裁剪在内部矩阵中是主要失败区；10 秒中段裁剪历史观察仅 `3/9` 通过。

## 4. 性能指标

宣传图只展示**核心算法参考耗时**，不展示用户实际处理链路：

- 写入：只统计 `WatermarkService::embed`。
- 读取：只统计 `WatermarkService::extract`。
- 不包含桌面端文件选择、格式探测、FFmpeg 转码、文件读写、版权记录或 UI 等待。
- 不把一次完整动作的总时长拆写成单独的写入或读取时间。

### 4.1 可用于宣传的 release 基准

2026-07-31 已完成固定用户可感知素材桶的宣传专项基准，宣传图优先使用以下结果：

| 用户可理解的素材 | 写入平均 | 写入 p95 | 读取平均 | 读取 p95 |
| --- | ---: | ---: | --- |
| 约 10.8 MiB、12 MP JPEG | 985.73 ms | 1191.40 ms | 49.00 ms | 56.65 ms |
| 约 19.3 MiB、3 分钟 FLAC | 2284.72 ms | 2387.16 ms | 221.83 ms | 252.12 ms |

建议宣传图显示为：

- 图片：**约 10 MB 高清图片｜写入约 0.99 秒｜读取约 0.05 秒**
- 音频：**约 20 MB 高品质音频｜写入约 2.28 秒｜读取约 0.22 秒**

图片规格为 JPEG、4000×3000、12 MP；音频规格为 FLAC、180 秒、44.1 kHz、双声道、16-bit。每组 5 份确定性标准化素材，每份预热 1 次、正式测量 5 次，共 25 次/操作。

图片写入包含 JPEG 解码、共享核心写入和 PNG 保护副本编码。音频写入包含 FLAC→WAV 准备和 WAV 核心写入。读取均对内存中的正式保护副本调用共享核心，不包含磁盘读取或桌面 UI。

完整口径见 `docs/宣传性能专项基准v1.md`。这些数据只代表固定测试设备和标准化素材，不代表任意素材或用户端完整等待时间。

### 4.2 其他性能数据（不用于主宣传图）

| 样本 | 写入 | 读取 | 口径 |
| --- | ---: | ---: | --- |
| 17 张历史真实图片样本 | 平均 258.2 ms/张 | 基线 PNG 平均 332.5 ms；最大 3387 ms | 旧版 `robustness_bench`，仅核心算法 |
| 9 首历史真实音频样本 | 平均 306.8 ms/首 | 生产项平均 30.5 ms；17–113 ms | 旧版 `robustness_bench`，仅核心算法 |
| 102 个干净图片变体 | 不适用 | 平均拒绝 184 ms；最慢 373 ms | V3 图片误报拒绝 Gate |

旧版差分快照中的 `9659 ms / 13 ms` 与 `631 ms / 1126 ms` 是完整差分动作或特定基线入口的结果，不能解释为当前宣传口径下的“单独写入 / 单独读取”，因此不再用于宣传图。

### 4.3 其他完整链路数据

以下数据保留用于研发资源评估，不放入主宣传图：

- 常规图片，2–4 MP：完整产品管线约 8–24 秒。
- 接近 100 MP 的真实大图组：约 17–19 分钟，高资源场景。
- 音频 20:00 / 48 kHz / stereo / 24-bit FLAC：完整链路约 57.5 秒。

它们不是单独写入或读取耗时，也不是固定 SLA。

### 4.4 扰动图片读取量级

历史 17 图基准曾记录：

- 原始 PNG、PNG 重编码、JPEG q90/q75、中心遮盖、横向切割：多数平均约 0.3 秒。
- 90/180/270 度旋转：平均约 0.14–0.54 秒。
- 镜像：平均约 0.74–0.92 秒。
- 亮度、噪点、缩放、裁切等需要更深扫描的场景：平均约 1.5–4.0 秒，个别最大约 9 秒。

后续 V3 空间恢复优化曾将特定 15% 纵向切割的 17 图平均读取降至约 148.5 ms。由于版本与路径已变化，上述数据只用于说明“恢复型读取可能显著慢于原图读取”，不作为当前 SLA。

## 5. 质量与可靠性指标

### 5.1 图片

- 三张真实照片的保护副本质量：PSNR `44.11–51.29 dB`、SSIM `0.9951–0.9981`。
- 三张真实照片 × 三独立 UID × 八个承诺变换：`72/72` UID 精确匹配，独立核心读取与安装版只读验证均通过。
- 34 个 Windows 图片源生成 PNG/JPEG/WebP 共 102 个干净变体：误报 `0/102`。
- 这些样本量可支撑当前发布门禁，但不足以证明面对任意图片分布时误报率为零。

### 5.2 音频

- 五种正式输入格式 × mono/stereo：安装版基线 `10/10` 通过。
- 30 秒、48 kHz、五容器 × mono/stereo 的内部扰动矩阵中，基线、WAV 重编码、音量 80%、音量 120%、MP3 192k 往返共 `50/50` 通过。
- 同一完整矩阵的失败集中在 5–15 秒短裁剪及其组合，短裁剪不属于当前产品承诺。
- 噪声底素材曾出现“水印可读但感知质量未过门”的情况，因此不能宣传“所有音频绝对无感”。

## 6. 当前不能承诺的能力

- BMP、GIF、TIFF、RAW、PSD、SVG、动画 PNG/WebP 的正式图片保护。
- 任意小尺寸图片都可保护，或固定某个未经样本池验证的最低分辨率。
- 超过 100 MP 或 512 MiB 的图片。
- 超过 20 分钟、512 MiB、48 kHz、双声道的音频。
- 音频短裁剪、重新编辑或任意后处理后仍稳定读取。
- 图片多种扰动叠加后的稳定读取。
- 视频画面盲水印已经商业开放。
- 移动端已经具备与 Windows 桌面相同的发布状态、性能或资源上限。
- SDK/API、公共 Resolver、云处理、生产凭据或 SLA 已经开放。
- 版权编号或技术报告等于国家版权登记、司法鉴定、第三方公证、首次创作时间或法律权属结论。

## 7. 指标体系扩展建议

当前数据已经能回答“能处理什么”和“典型任务大概多久”，但还不能形成稳定性能 SLA。建议后续建立统一基准：

### 7.1 固定测试机信息

- CPU、逻辑核心数、内存、磁盘类型。
- Windows 版本、HiddenShield 版本、`watermark-core` commit。
- 冷启动/热启动、是否命中系统文件缓存。
- 输入位于本地 SSD、移动硬盘还是网络盘。

### 7.2 固定素材分桶

图片按以下维度统计：

- 像素：1 MP、4 MP、12 MP、24 MP、50 MP、100 MP。
- 格式：PNG、JPEG、WebP。
- 内容：照片、插画、UI/文字、低纹理、深色噪声、细节密集。
- 文件大小：小于 5 MiB、5–50 MiB、50–200 MiB、200–512 MiB。

音频按以下维度统计：

- 时长：30 秒、1 分钟、5 分钟、10 分钟、20 分钟。
- 格式：WAV、MP3、FLAC、OGG、M4A。
- 规格：8/16/22.05/44.1/48 kHz，mono/stereo，16/24/32-bit。
- 内容：音乐、人声、播客、环境声、低噪声底、高动态范围。
- 文件大小：小于 10 MiB、10–100 MiB、100–512 MiB。

### 7.3 固定输出指标

每个分桶至少记录：

- 写入 p50 / p95 / p99。
- 原保护副本读取 p50 / p95 / p99。
- 扰动副本读取 p50 / p95 / p99。
- 完整产品链路 p50 / p95 / p99。
- 峰值工作集、进程树峰值、输出文件大小变化。
- 成功率、误报率、漏报率、失败原因分布。
- 图片 PSNR/SSIM；音频 SNR/LUFS/峰值差异/新增削波。

### 7.4 建议首轮性能目标

以下是建议目标，不是当前承诺：

| 场景 | 建议目标 |
| --- | ---: |
| 4 MP 图片完整写入 | p95 ≤ 15 秒 |
| 4 MP 图片原保护副本读取 | p95 ≤ 2 秒 |
| 4 MP 图片单项扰动读取 | p95 ≤ 5 秒 |
| 30 秒音频完整写入 | p95 ≤ 5 秒 |
| 30 秒音频读取 | p95 ≤ 2 秒 |
| 20 分钟音频完整写入 | p95 ≤ 90 秒 |
| 干净图片无水印拒绝 | p95 ≤ 1 秒 |

这些目标应在统一测试机和至少 30 个样本/分桶上复测后，才能决定是否进入产品 SLA。

## 9. 推荐下一步

建立 `performance-baseline-v1`：在同一台 Windows 测试机上，先跑 30 个 4 MP 图片样本和 30 个 30 秒音频样本，统一记录核心写入、核心读取、完整链路、p50/p95/p99、峰值内存和失败原因，并将原始 JSON artifact 纳入可追溯归档。
