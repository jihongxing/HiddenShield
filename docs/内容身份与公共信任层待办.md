# HiddenShield 内容身份与公共信任层待办

更新时间：2026-07-26

状态：`suspended_by_user`

实施状态：`未实施，不进入当前开发、RC 或 GA 主线`

## 1. 决策摘要

HiddenShield 当前继续保持既有正式架构与能力边界：

- Watermark ID 保持 `HS-XXXXXXXX-XXXXXXXX-XXXXXXXX-XXXXXXXX` 的 128-bit 不透明锚点格式。
- 图片 / 音频默认媒体 payload 保持 V3 / 39-byte 最小锚点，不增加 issuer、权利声明、完整哈希或非对称签名。
- `watermark-core` 继续作为所有正式盲水印写入、读取、认证、版权编号和跨端互验算法的唯一事实源。
- 本地版权库、云端 registry、公开权利查询、公开元数据、报告和 C2PA 传播层继续按现有能力边界运行。
- 当前不修改代码、数据库、API、SDK、协议、fixture、报告、商业权益或用户界面。

本待办仅完整记录已经发现的公共信任层问题、建议解决方向、恢复条件和未来验收要求。用户已决定暂时挂起，不安排实施日期。

## 2. 为什么记录这个问题

HiddenShield 已经完成从“随机短编号工具”到“鲁棒内容锚点系统”的主要架构迁移：

```text
Opaque Watermark ID
        ↓
V3 Embedded Minimal Anchor
        ↓
Local / Cloud Registry Record
        ↓
Public Rights Metadata / Report / C2PA
```

现有系统能够完成：

- 从保护副本读取 Watermark ID。
- 在支持的图片 / 音频正式端点之间跨端互读。
- 使用本地版权库或云端 registry 解释版本、声明、登记状态和公开权利信号。
- 生成本地证据摘要、公开元数据和报告材料。
- 表达 `legalConclusion=false`，避免把技术记录包装成法律权属结论。

但当前系统的“自校验”和“第三方独立验证”之间仍有一条未闭合的信任边界：

```text
当前已具备：
读取锚点 + 查询记录 + HMAC 认证 + 服务端返回状态

尚未形成统一生产能力：
第三方仅持有公钥 / 证书链，即可独立验证某项登记事实确由指定 issuer 签发
```

该问题不影响当前 V3 锚点的读取和本地版权记录使用，但会影响未来公开协议、企业签发、长期证据验证、公开 SDK 和平台互操作的可信上限。

## 3. 已确认可以长期保持的原则

### 3.1 Watermark ID 只负责标识

Watermark ID 必须继续保持：

- 不透明。
- 高熵。
- 全局稳定。
- 不携带创作者、设备、账号、时间、文件哈希或 issuer 明文。
- 不因权利声明、登记状态或签名算法变化而改变格式。

冻结原则：

```text
Watermark ID 只负责标识，不负责表达。
```

当前架构属于基于不透明锚点寻址的内容来源系统，不应称为严格的 content-addressable 系统，因为 Watermark ID 不是由内容哈希直接计算得到。

### 3.2 媒体内只保留最小鲁棒锚点

图片 / 音频 V3 媒体 payload 当前只保留：

- `watermark_id`
- `payloadProtocolVersion`
- `auth_tag`

这是容量、鲁棒性、性能和跨端可读性的共同结果。完整权利语义、版本关系、登记状态和声明应继续放在版权库、registry、公开元数据或签名凭证中。

未来公共信任层不得以“增加可信度”为理由，把 issuer、完整签名、权利声明或可变状态重新塞回 Watermark ID 或默认 V3 媒体 payload。

### 3.3 盲水印与 C2PA 是互补层

长期定位应保持：

- 盲水印提供在元数据被剥离、转码或常见二次处理后仍可尝试恢复的鲁棒身份锚点。
- C2PA、XMP、IPTC / PLUS、JSON-LD 等公开元数据提供可互操作的声明和签名传播层。
- registry 提供当前状态、撤销、替代、版本、公开权利信号和在线查询。

不得把 HiddenShield 盲水印描述为替代或对抗 C2PA。正确关系是鲁棒锚点与公开签名声明互补。

### 3.4 历史事实与当前状态分离

未来信任模型应遵守：

```text
锚点不删除；
历史签发事实不静默改写；
凭证、声明和报告可以被撤销或替代；
在线服务负责解释当前状态。
```

## 4. 已发现的问题

### 4.1 `auth_tag` 的完整性语义与签发语义容易混淆

`watermark-core` 当前 V2 / V3 `auth_tag` 使用 HMAC-SHA256。当前实现中的共享秘密位于客户端核心库代码路径中。

它适合表达：

- payload 结构通过 HiddenShield codec 认证。
- payload 未发生随机损坏或不匹配。
- 当前正式读取端能够识别认证标签。

它不适合表达：

- HiddenShield 云端正式签发。
- 某个 Enterprise issuer 签发。
- 某个创作者、账号或设备完成身份签名。
- 某条版权声明经过第三方认证。
- 法律权属成立。
- 第三方只依赖公开密钥即可独立验证签发主体。

风险：

- 文档、UI 或报告若把 `auth_tag` 称为“数字签名”或“官方签名”，会造成过度承诺。
- 将来公开第三方写入 SDK 后，共享 HMAC 秘密不能承担 issuer 不可伪造性。
- 法务或企业客户可能追问“由谁签发、使用哪把密钥、密钥当时是否有效、现在是否撤销”，当前 payload auth tag 无法单独回答。

建议解决方向：

- 将 `auth_tag` 统一称为 `payload authentication tag` 或“载荷认证标签”。
- 验证结果中将 `anchorIntegrity` 与 `credentialSignature` 分开。
- 不修改 V3 payload；在媒体外新增非对称签名凭证。

### 4.2 当前 registry receipt 不是公开可验证的签名凭证

当前后端 `registry_receipt` 形态为：

```text
hsreg:v1:{registry_id}:{watermark_uid}:{status}:{proof}
```

其中 `proof` 是摘要前缀，不是非对称数字签名。

当前 receipt 可以作为：

- 服务端登记流程中的收据标识。
- registry proof hash 的输入。
- 客户端记录和同步字段。

但不能作为：

- 第三方离线验证的 issuer 签名凭证。
- 明确绑定 `issuerId`、`keyId`、签名算法和证书链的长期证据。
- 可独立验证的登记事实标准格式。
- 带有规范撤销、替代和密钥轮换语义的公共 credential。

建议解决方向：

- 保留现有 receipt 作为历史兼容字段。
- 未来新增版本化 Signed Registry Credential，而不是在现有字符串后面追加越来越多字段。
- Signed Registry Credential 使用规范化 JSON 或 CBOR，并为签名输入建立跨语言 fixture。

### 4.3 Issuer 与 Key 模型分散在多个子系统

项目当前已经分别存在：

- PDF 报告的 `signerKeyId`、证书链、KMS / HSM、OCSP / CRL 和长期验证设计。
- 离线许可证的 Ed25519 issuer、trust policy、密钥轮换和撤销列表。
- C2PA 的生产证书链、TSA 和 signer 配置。
- rights manifest 的 `signature`、`signedBy`、替代和撤销字段。
- 公开元数据 `signedManifestStore` 的 HMAC 原型。

这些说明 issuer/key 问题并非完全没有设计，而是尚未形成跨对象统一合同。

未统一的问题包括：

- `issuerId` 的全局命名规则。
- `keyId` 的稳定格式。
- 公钥或证书链如何发现。
- 一把密钥允许签发哪些 artifact。
- 本地设备、HiddenShield registry、Enterprise 和外部平台的可信等级。
- 密钥有效期、轮换、verify-only、撤销和历史验证。
- 不同签名对象是否共享根信任。

建议解决方向：

```text
Trust Root
  └── Issuer
       └── Key
            ├── Registry Credential
            ├── Rights Manifest
            ├── Evidence Report
            └── C2PA Manifest
```

未来应定义统一 Issuer Document 和 Key Document，但不同 artifact 可以使用不同 key usage 和证书 profile。

### 4.4 撤销能力已经存在，但缺少统一对象状态模型

当前项目已经存在：

- rights manifest 的 `active`、`revoked`、`superseded`。
- `supersededBy` 和 `revokedAt`。
- 报告的 `active`、`superseded`、`revoked`。
- 报告签名证书的 OCSP / CRL 设计。
- Watermark ID 的 reconcile、conflict 和 reissue。
- 离线许可证和 API key 撤销。

真正未闭合的是：

- 撤销的是锚点、登记记录、签名凭证、权利声明、报告还是 issuer key。
- 一个对象被撤销后是否影响其他对象。
- `reissued`、`superseded`、`revoked`、`conflict` 的统一关系。
- replacement Watermark ID、successor credential 和替代 rights manifest 如何互相引用。
- 离线撤销列表覆盖哪些对象以及数据新鲜度如何表达。

建议解决方向：

- 每种对象保持独立状态，不做隐式级联撤销。
- Watermark ID 继续可读取，不因 registry 状态变化而变成无效字节。
- 在线 resolver 返回当前状态和替代关系。
- 离线验证显示撤销数据生成时间、有效期和新鲜度。
- 撤销必须保留原因码、操作主体、操作时间和审计事件。

### 4.5 AI 与真实性信息已有声明层，但外部证据尚未泛化

当前 V3 已把 AI 生成、训练许可、真实性和创作方式等可变语义迁出媒体 payload，并通过 rights manifest、registry、公开元数据和 C2PA / CAWG 映射表达。

这已经实现了：

- 用户自声明。
- 声明版本化。
- 声明撤销和替代。
- 公开扫描。
- `legalConclusion=false`。

未来可能增加的平台签名 evidence，但不能把所有声明强制升级为外部证明。

建议证据等级：

- `self_declared`
- `device_signed`
- `registry_signed`
- `platform_signed`
- `externally_verified`
- `unsupported_proof`
- `invalid_proof`

重要边界：

- 没有 proof 的声明仍可保存，但必须显示为自声明。
- 平台签名只证明平台签署了某项声明，不自动证明声明客观真实。
- HiddenShield 不因读取到 AI evidence 就自动进行 AI 生成检测或法律授权判断。

### 4.6 当前公开签名原型仍不是生产信任链

公开元数据 `signedManifestStore` 当前使用 HMAC-SHA256 和开发 fallback secret，并明确属于 C2PA-compatible 原型。

它不能被表述为：

- 生产 C2PA 信任锚。
- 公共 CA 证书链。
- 第三方仅使用公开密钥即可独立验证。
- 已部署的长期签名和撤销服务。

未来生产化必须继续服从现有 C2PA、TSA、KMS / HSM 和外部 SDK 发布门禁。

## 5. 建议的目标架构

### 5.1 四层职责

```text
1. Anchor ID
   只负责稳定标识和查询寻址

2. Embedded Anchor
   只负责鲁棒嵌入、读取和载荷认证

3. Signed Credential
   负责证明某个 issuer 在某个时间签发了某项登记事实

4. Registry Resolver
   负责返回当前状态、撤销、替代、issuer/key 材料和公开权利信号
```

### 5.2 验证状态必须分离

未来验证结果不应合并成单一“可信”字段，至少分为：

- `anchorIntegrity`
  - `verified`
  - `invalid`
  - `not_available`
- `credentialSignature`
  - `valid`
  - `invalid`
  - `not_present`
  - `not_evaluated`
- `issuerTrust`
  - `trusted`
  - `untrusted`
  - `unknown`
  - `not_evaluated`
- `registryStatus`
  - `active`
  - `pending`
  - `conflict`
  - `superseded`
  - `revoked`
  - `not_found`
  - `offline_unknown`
- `trustedTime`
  - `valid`
  - `invalid`
  - `not_timestamped`
  - `not_evaluated`
- `legalConclusion`
  - 固定为 `false`

### 5.3 Signed Registry Credential 建议字段

以下仅作为未来设计输入，当前没有冻结 wire format：

```json
{
  "credentialVersion": "hs-registry-credential-v1",
  "credentialId": "hsrc_...",
  "watermarkUid": "HS-...",
  "registryId": "wmreg_...",
  "registryStatus": "active",
  "issuedAt": "2026-07-26T00:00:00Z",
  "subjectDigest": {
    "algorithm": "sha256",
    "value": "..."
  },
  "issuerId": "issuer:...",
  "keyId": "key:...",
  "signatureSuite": "...",
  "signature": "..."
}
```

未来正式设计还必须决定：

- canonicalization 规则。
- JSON、CBOR 或双格式。
- credential 是否包含到期时间。
- 是否直接包含公钥、证书链，或只引用 issuer/key document。
- subject digest 绑定 registry 记录、rights manifest 还是独立 canonical claims。
- replacement 和 revocation 引用。
- 未知扩展字段是否进入签名输入。

这些问题当前均不实施、不冻结。

### 5.4 不预先锁死签名算法

Ed25519 可以作为候选，但当前不把公共协议永久写死为 Ed25519，原因包括：

- 需要与生产 KMS / HSM 支持情况对齐。
- 需要与 C2PA 证书链和企业客户 PKI 对齐。
- 需要确认 Rust、TypeScript、Dart、Windows、Android 和 iOS 的稳定验证实现。
- 不同 artifact 可能需要不同签名 profile。

建议未来通过 `signatureSuite` 注册表扩展，并在完成互操作性评审后冻结首个生产 profile。

## 6. 未来恢复时的实施顺序

### Phase 0：术语与边界修正

- 全仓检查 `auth_tag`、签名、认证、可信、公证、登记和权属相关文案。
- 明确 payload 认证、credential 签名、issuer trust、registry 状态和法律结论的区别。
- 不修改 V3 payload 字节布局。

### Phase 1：Trust Status Vocabulary

- 冻结统一验证维度和状态枚举。
- 冻结 issuer 类型和可信等级。
- 冻结对象级撤销边界。
- 输出跨桌面、移动、后端、SDK 和报告的字段契约。

### Phase 2：Signed Registry Credential

- 定义 canonical credential。
- 定义签名输入和 signature suite。
- 定义 issuer/key 引用。
- 定义替代、撤销和历史验证。
- 生成跨语言固定 fixture。

### Phase 3：Issuer / Key Registry

- 实现 issuer document。
- 实现 key document。
- 实现公钥或证书链发现。
- 实现轮换、verify-only 和撤销。
- 接入生产 KMS / HSM 或等价托管。

### Phase 4：扩展现有公开 Resolver

继续使用现有：

```text
GET /v1/public/rights/{watermarkUid}
POST /v1/public/rights/batch
GET /v1/public/rights/{watermarkUid}/metadata
```

不创建语义重复的第二套 `/resolve` 服务。

未来扩展响应：

- signed credential。
- issuer/key 引用。
- 分离的验证状态。
- replacement / revocation。
- 离线缓存和数据新鲜度信息。

### Phase 5：扩展现有只读 SDK

在现有公开扫描 SDK 基础上增加：

- credential canonicalization。
- 非对称签名验证。
- issuer/key resolution。
- 离线 credential 验证。
- 撤销列表和新鲜度验证。
- 明确的用户文案映射。

第三方写入 SDK 继续保持受控，不与免费只读验证 SDK 同时无门槛开放。

## 7. 未来验收标准

恢复实施后，至少需要以下验收：

### 7.1 跨语言确定性

- Rust、TypeScript 和 Dart 对同一 credential 生成完全相同的 canonical bytes。
- 同一签名 fixture 在桌面、Android、iOS、后端和外部 SDK 中得到一致结果。

### 7.2 签名与篡改

- 有效 credential 通过。
- 任一受签字段修改后失败。
- 错误 `keyId`、错误 issuer、错误算法和截断签名失败。
- 未知扩展字段按冻结规则处理，不产生跨实现差异。

### 7.3 密钥生命周期

- 当前有效 key 通过。
- verify-only 历史 key 可验证历史 credential。
- 过期 key 的历史验证按可信时间策略解释。
- revoked key 显示撤销，不静默降级为普通失败。
- key rotation 和 rollback 有审计证据。

### 7.4 对象状态

- active、conflict、superseded、revoked 和 replacement 关系可查询。
- 撤销 rights manifest 不自动删除 Watermark ID。
- 撤销报告不自动撤销 registry credential。
- 撤销 issuer key 能准确标记受影响凭证范围。

### 7.5 离线与在线

- 无服务器时可以读取 V3 锚点。
- 持有 credential 和公钥材料时可以离线验证历史签名事实。
- 离线撤销信息过期时必须显示 freshness 风险。
- 当前 registry 状态无法离线确认时显示 `offline_unknown`，不得显示 active。

### 7.6 V3 与跨端回归

- V3 / 39-byte payload 字节布局不变。
- desktop-written/mobile-read 和 mobile-written/desktop-read 图片、音频 fixture 继续通过。
- 新信任层不得降低水印写入质量、提取性能或鲁棒性。
- 旧客户端能够忽略新增 resolver 字段，不发生协议崩溃。

### 7.7 能力边界

- 所有公开输出继续保持 `legalConclusion=false`。
- 不把平台签名 evidence 表述为 AI 检测结论。
- 不把自签名、fixture、开发 HMAC 或测试证书表述为生产信任链。
- 没有生产 KMS / HSM、证书链、TSA、撤销服务和外部 SDK 验收时，不升级为可对用户承诺。

## 8. V3 当前版本的进化与优化方向

本节回答一个核心问题：

```text
在不扩大 V3 / 39-byte payload、不增加媒体失真、不破坏跨端互验的前提下，
HiddenShield 当前版本以后应该怎样进化？
```

总体策略：

```text
冻结媒体锚点；
演进媒体外协议；
统一信任语义；
强化验证与运营；
只在有量化证据时考虑新媒体 payload 版本。
```

### 8.1 版本进化目标

当前版本的优化目标不是“让水印携带更多信息”，而是：

- 让同一个 V3 Watermark ID 能够关联更完整、可升级的媒体外事实。
- 让第三方可以区分载荷完整性、签发真实性、issuer 可信度、登记状态和法律边界。
- 让声明、证据、撤销和替代能够独立版本化。
- 让旧 V3 保护副本在未来信任层升级后仍然有效。
- 让桌面、移动、后端和公开 SDK 使用同一套验证状态与用户语义。
- 让新增公共信任能力不影响当前图片 / 音频质量、容量、性能和鲁棒性。

### 8.2 V3 媒体协议保持冻结

当前正式 V3 / 39-byte payload：

```text
magic                  4 bytes
protocol version       1 byte
payload length         2 bytes
watermark ID          16 bytes
auth tag              16 bytes
────────────────────────────
total                  39 bytes
```

未来公共信任层建设默认不得修改：

- `watermark_id` 长度。
- `auth_tag` 长度。
- V3 payload 总长度。
- V3 magic、版本识别和字段偏移。
- 图片 sync packet 和音频 recovery packet 的正式 V3 语义。
- 现有跨端 fixture 的 Watermark ID 恢复结果。

原因：

- 当前 39 bytes 已经处于 Anchor + auth tag 的合理容量区间。
- payload 每增加一项信息，都会消耗冗余、鲁棒性、感知质量、最低素材条件或处理性能中的至少一项。
- issuer、AI claim、权利状态、撤销和签名算法均属于可变语义，不适合固化在不可变媒体载荷中。
- 媒体内字段越多，桌面、移动、后端 worker 和未来 SDK 的兼容成本越高。

### 8.3 不把公共信任层升级命名为 V4

未来新增 Signed Registry Credential、Issuer Document、Key Document、Rights Evidence 或 Resolver 状态，不等于水印 payload 升级。

建议分别版本化：

| 对象 | 建议版本空间 | 是否改变 V3 payload |
| --- | --- | --- |
| 媒体锚点 | `watermark-payload-v3` | 是，仅真正媒体协议变更时 |
| Registry Credential | `hs-registry-credential-v1` | 否 |
| Rights Manifest | `hs-rights-manifest-vN` | 否 |
| Evidence | `hs-rights-evidence-vN` | 否 |
| Issuer Document | `hs-issuer-document-v1` | 否 |
| Key Document | `hs-key-document-v1` | 否 |
| Resolver Response | API 版本或 additive schema | 否 |
| Verification Result | `hs-verification-result-v1` | 否 |

只有出现以下情况之一，才允许讨论 V4：

- V3 Watermark ID 的 128-bit 身份空间被证明不足。
- V3 auth tag 出现无法通过媒体外机制缓解的实质安全问题。
- 正式媒体算法需要不可兼容的新同步或纠错语义。
- 有量化测试证明新增媒体内字段带来的价值高于质量、鲁棒性和兼容成本。
- 桌面、Android、iOS、后端和所有正式读取端都有完整迁移方案。

任何“为了多放几个 flags”或“为了让 ID 更自解释”的需求，都不能单独成为 V4 理由。

### 8.4 不在默认 payload 中加入可选 flags

曾讨论过在媒体内增加少量 bit：

- AI flag。
- media type。
- issuer class。
- proof hint。
- rights manifest presence。

即使这些字段只需要 1～2 bytes，也不建议进入默认 V3，原因包括：

- AI 和权利声明会被修改、撤销或替代。
- `AI = 0` 无法区分“声明非 AI”“未声明”“旧版本默认值”或“证据缺失”。
- issuer class 无法表达具体 issuer、key、信任状态和密钥轮换。
- proof hint 不能代替 proof 验证，反而容易被 UI 过度解释。
- 可选字段会形成不同容量和读取 profile，增加跨媒体和跨端兼容复杂度。

如果未来确有媒体内 proof fragment 的业务需求，必须：

- 作为独立实验 profile，不改变正式 V3 默认写入。
- 先定义无法通过 registry、sidecar、C2PA 或报告解决的明确场景。
- 单独评估容量、感知质量、鲁棒性、最低素材条件和跨端读取。
- 在所有正式端点支持前，不进入正式版权记录、报告或公开能力承诺。

### 8.5 优先优化媒体外事实模型

V3 后续进化的主要施工面应是媒体外对象，而不是 payload。

优先级建议：

#### P0：统一术语和验证结果

- `auth_tag` 统一称为载荷认证标签。
- 分离 `anchorIntegrity`、`credentialSignature`、`issuerTrust`、`registryStatus`、`trustedTime` 和 `legalConclusion`。
- 桌面、移动、后端、报告和 SDK 使用同一枚举和文案映射。
- 禁止把“读取成功”“认证通过”“registry active”合并成单一“版权可信”结论。

预期改善：

- 降低用户和法务对 HMAC、数字签名与权属的混淆。
- 为未来 credential 接入预留稳定 UI 和 API 位置。
- 不改变任何媒体字节或算法。

#### P1：把登记事实升级为独立 Signed Registry Credential

Credential 只证明：

- 哪个 issuer。
- 使用哪把 key。
- 在什么时间。
- 对哪个 Watermark ID / registry record。
- 签署了哪一组规范化登记事实。

不建议把全部 AI、License 和当前状态都永久写进同一个 credential。

预期改善：

- 第三方可以独立验证登记签发事实。
- 现有 V3 保护副本无需重写。
- PDF、C2PA、rights manifest 和公开 SDK 可以引用同一 credential。

#### P2：拆分 Rights Claim 与 Evidence

Rights Manifest 负责表达：

- 创作方式声明。
- AI 生成声明。
- 训练许可。
- 真实性声明。
- 自定义许可条款。

Evidence 负责表达：

- 声明来源。
- provider / platform。
- subject digest。
- issuer / key。
- 签名。
- 验证结果。

允许：

```text
claim without proof
claim + device proof
claim + registry proof
claim + platform proof
claim + external verification
```

预期改善：

- 保留本地创作者低门槛声明。
- 允许未来平台提供更高可信 evidence。
- 不把平台签名错误解释为客观真实性证明。

#### P3：扩展现有 Resolver，而不是新建第二套服务

在现有公开权利 API 上 additive 扩展：

- credential。
- issuer/key 引用。
- 当前撤销和替代状态。
- 验证维度。
- 数据更新时间和离线 freshness。

预期改善：

- 保持现有调用方兼容。
- 避免 `/resolve` 与 `/public/rights` 双事实源。
- 保持 registry 为当前状态真源。

#### P4：扩展现有只读 SDK

未来 SDK 应形成：

```text
scan anchor
    ↓
resolve record
    ↓
verify credential
    ↓
evaluate issuer/key
    ↓
evaluate current status
    ↓
format non-legal user result
```

预期改善：

- 第三方不需要理解 HiddenShield 内部数据库结构。
- 在线和离线验证可以使用相同结果模型。
- 免费只读验证与收费签发服务可以清晰分离。

#### P5：统一密钥、撤销和历史验证运营

- issuer/key usage 明确区分 registry、report、rights、C2PA 和 license。
- 历史 key 进入 verify-only，不重签历史事实。
- key revoked、credential revoked、rights revoked 和 report revoked 分开表达。
- 在线状态和离线状态列表都有生成时间、有效期和审计来源。

预期改善：

- 支撑长期证据验证。
- 避免不同子系统各自维护不兼容 trust policy。
- 为 Enterprise PKI、KMS / HSM 和 SLA 做准备。

### 8.6 优化版本链，而不是立即建设内容演化图

当前 `parentWatermarkUid + revision` 继续用于线性版本和重签发。

近期可以改善：

- 明确 `reissue` 是纠错 / 重签关系，不自动等于内容新版本。
- 明确 `superseded` 是当前有效记录替代关系，不删除旧记录。
- 明确 `conflict` 是待仲裁状态，不自动选择某一条为真。
- 在记录和 resolver 中提供明确 replacement / predecessor 引用。

暂不承诺：

- 多父节点合并。
- 任意 DAG。
- 自动推导内容派生关系。
- 自动判断哪个版本拥有更高法律效力。
- 用相同边同时表达内容修改、权利转移和登记纠错。

只有在出现真实分支工作流后，才设计独立的 evolution relation type。

### 8.7 优化本地与云端的职责边界

本地继续负责：

- 原始文件和保护副本。
- 完整 SHA-256。
- 本地声明和证据材料。
- 离线读取和匹配。
- 用户隐私控制。

云端继续负责：

- Watermark ID 登记。
- 当前 registry 状态。
- 多设备同步。
- rights manifest 和公开权利查询。
- credential、issuer/key 和撤销材料。
- 企业 SLA 与审计。

未来改善时应避免：

- 为了验证 credential 强制上传原始媒体。
- 把本地路径、创作者明文身份或完整私有证据放入公开 resolver。
- 云端不可用时把历史离线签名事实直接判定为无效。
- 离线状态过期时错误显示为当前 active。

### 8.8 优化用户可见验证表达

未来 UI 和报告应分别回答：

1. 是否读到 HiddenShield Watermark ID？
2. payload 认证是否通过？
3. 是否匹配本地版权记录？
4. 是否存在 registry 记录？
5. credential 签名是否有效？
6. issuer 是否在当前 trust policy 中？
7. 当前记录是否 active、superseded、revoked 或 conflict？
8. 是否有可信时间证明？
9. 声明是 self-declared、signed 还是 externally verified？

禁止合并为：

- “版权有效”。
- “官方认证原创”。
- “法院认可”。
- “已证明非 AI”。
- “已证明拥有全部权利”。

预期改善：

- 用户知道系统证明了什么。
- 企业和法务能读取更细的证据层级。
- 当前谨慎的能力边界得到持续保持。

### 8.9 优化质量、容量与性能治理

未来任何媒体 payload 变更提案必须同时提交：

- 字节和 bit 增量。
- 每种媒体的有效载荷和纠错开销。
- 图片 PSNR / SSIM / 感知差异结果。
- 音频 SNR / LUFS / 峰值 / clipping / ABX 结果。
- 视频 PSNR / SSIM / VMAF 和真实转码矩阵。
- 最低图片尺寸、最低音频时长和视频容量变化。
- 写入、写后验证和只读提取耗时变化。
- desktop / Android / iOS / backend worker 跨端 fixture。
- rollback 和旧数据读取方案。

默认决策规则：

```text
能放在媒体外解决的问题，不增加媒体 payload。
不能证明用户价值大于质量与兼容成本的字段，不进入媒体 payload。
```

### 8.10 兼容与迁移策略

未来公共信任层升级应满足：

- 旧 V3 保护副本无需重新写入即可关联新 credential。
- 现有 Watermark ID 不重新生成。
- 现有 registry record 通过 backfill 或附加对象获得 credential，不重写历史时间。
- 旧客户端忽略新增 resolver 字段后仍能查询基础权利结果。
- 新客户端面对没有 credential 的旧记录时显示 `credentialSignature = not_present`，而不是判定锚点无效。
- V2 legacy 继续按已有迁移边界处理，不因公共信任层重新恢复为默认正式写入。
- 任何迁移都保留原始 receipt、旧状态和审计记录。

### 8.11 当前版本优化优先级

在待办恢复后，建议按以下顺序评审，不允许跳过前置语义直接开发：

| 优先级 | 优化项 | 是否修改媒体 payload |
| --- | --- | --- |
| P0 | 术语、验证状态和能力边界统一 | 否 |
| P1 | Signed Registry Credential 合同 | 否 |
| P2 | Issuer / Key / signature suite 合同 | 否 |
| P3 | Rights Claim 与 Evidence 分层 | 否 |
| P4 | 统一撤销、替代和历史状态 | 否 |
| P5 | 扩展现有 Resolver 与只读 SDK | 否 |
| P6 | 生产 KMS / HSM、证书链、TSA 和运营门禁 | 否 |
| P7 | 评估是否存在必须修改媒体 payload 的真实需求 | 仅评估 |

结论：

```text
当前版本进化的主要空间在媒体外信任层，
而不是把 V3 / 39-byte payload 扩大成新的全量协议。
```

## 9. 候选架构公理审查

本章记录对后续讨论中六条“架构公理”的正式审查结果。目的不是立即发布新的对外协议，而是区分：

- 可以作为长期内部原则冻结的内容。
- 方向正确但需要修正文案的内容。
- 当前证据不足、不能宣称为永久最优的内容。
- 必须继续保持待决的设计问题。

本章状态：

```text
reviewed_as_backlog
suspended_by_user
not_a_public_spec
```

### 9.1 公理一：V3/39 是当前正式最小锚点 profile

候选原表述：

```text
V3 payload（39 bytes）是工程 Pareto 最优点，
结构最小且永久冻结。
```

审查结论：`接受方向，修正强度`

可以冻结：

- V3/39 是 HiddenShield 当前正式图片 / 音频能力的最小锚点 profile。
- 当前公共信任层、AI evidence、rights、issuer/key、撤销和商业能力建设不得以增加语义为理由扩大 V3/39。
- 当前 V3 字节布局、Watermark ID 长度和 auth tag 长度继续作为跨端正式能力合同。
- 任何媒体协议升级都必须提供质量、容量、鲁棒性、性能、跨端迁移和旧数据读取证据。

不能冻结：

- “V3/39 已被数学证明为所有未来场景的全局 Pareto 最优”。
- “再减少任何一个字节都必然无法工作”。
- “未来永远不允许出现新的媒体 payload profile”。

原因：

- auth tag 长度、协议头编码和媒体冗余策略理论上仍存在不同安全 / 容量组合。
- 不同媒体的容量、纠错、感知质量和攻击模型并不相同。
- 当前可以冻结的是产品与兼容合同，不是对所有未来算法空间的数学证明。

建议内部冻结文案：

```text
V3/39 is the frozen minimal-anchor profile for the current
HiddenShield image and audio capability contract.

It must not be reopened for semantic expansion.
```

中文：

> V3/39 是当前 HiddenShield 图片和音频正式能力合同的冻结最小锚点 profile；不得为了增加媒体外可表达的语义而重新扩容。

### 9.2 公理二：Watermark ID 只负责寻址

候选原表述：

```text
Watermark ID is an opaque, non-semantic,
globally unique anchor identifier.
```

审查结论：`原则接受，唯一性措辞修正`

建议冻结定义：

```text
Watermark ID is an opaque, non-semantic,
globally scoped, collision-resistant anchor identifier.
```

中文：

> Watermark ID 是不透明、无业务语义、全局作用域且具备高碰撞阻力的锚点标识。

冻结约束：

- 不编码时间。
- 不编码 issuer。
- 不编码原文件或保护副本 hash。
- 不编码 AI 生成、训练许可或真实性声明。
- 不编码权利状态、撤销状态或当前 registry 状态。
- 不编码设备、账号、创作者身份或本地路径。
- 一经正式分配，不得复用于另一条无关记录。
- 后端签发和离线生成继续使用相同展示格式。

为什么不用绝对 `globally unique`：

- 128-bit 高熵编号提供极低碰撞概率，但随机空间不能在数学上承诺永不碰撞。
- 云端 registry 仍需执行唯一约束、冲突检测和 reissue / reconcile。
- 协议应描述可验证工程性质，避免绝对化措辞。

### 9.3 公理三：媒体内外严格分层

候选原表述采用三层：

```text
Layer 0：Media
Layer 1：Anchor Binding
Layer 2：Semantic Layer
```

审查结论：`方向接受，调整为四层`

建议长期模型：

```text
Layer 0：Embedded Anchor
  - watermark ID
  - payload authentication tag

Layer 1：Registration Credential
  - registry identity
  - digest binding
  - issuer / key
  - signed issuance facts

Layer 2：Claims And Evidence
  - rights manifest
  - AI claims
  - training permission
  - license
  - platform evidence
  - external verification evidence

Layer 3：Dynamic Status
  - active
  - pending
  - conflict
  - superseded
  - revoked
  - replacement
  - key status
  - status freshness
```

为什么需要 Layer 3：

- Credential 表达签发时形成的历史事实。
- Claims 可以独立修改、补充、撤销和替代。
- 当前 registry、key 和 revocation 状态会持续变化。
- 不能为了更新当前状态而覆盖原始 credential。
- 离线可验证的历史签名事实与在线当前状态不是同一结论。

冻结原则：

```text
Anchor identifies.
Credential attests issuance.
Claims express semantics.
Resolver reports current status.
```

### 9.4 公理四：auth tag 是载荷认证标签

候选原表述：

```text
authTag = Payload Authentication Code (PAC)
```

审查结论：`语义接受，不采用 PAC 缩写`

统一术语：

```text
payload authentication tag
载荷认证标签
```

不建议使用 PAC：

- PAC 不是当前项目已经冻结的协议术语。
- 可能与外部系统缩写冲突。
- “code”容易被误解为签发凭证或第三方签名。

建议冻结能力矩阵：

| 能力 | auth tag |
| --- | --- |
| 检测 payload 随机损坏或字段不匹配 | 支持 |
| 在当前 HiddenShield codec 边界内认证 payload | 支持 |
| 证明具体 issuer 身份 | 不支持 |
| 第三方仅使用公开密钥验证 | 不支持 |
| 证明创作者身份 | 不支持 |
| 证明 registry 正式签发 | 不支持 |
| 证明法律权属 | 不支持 |

不得在对外材料中表述为：

- 官方签名。
- 创作者签名。
- 权属签名。
- 第三方公证。
- 公共防伪证书。

“弱防伪”也不建议作为用户承诺，因为当前共享秘密存在于客户端核心实现中，未来开放第三方写入能力后不能承担公共 issuer 不可伪造性。

### 9.5 公理五：锚点不删除、不复用，状态可以撤销

候选原表述：

```text
Anchor is immutable and never revoked.
Only claims and credentials are revocable.
```

审查结论：`原则接受，撤销措辞修正`

不建议冻结“Watermark ID 永远不能被标记 revoked”，因为系统需要处理：

- 错误登记。
- ID 冲突。
- 法律要求。
- 恶意或欺诈记录。
- 密钥泄漏。
- replacement / reissue。

建议冻结为：

```text
An assigned Watermark ID is never silently deleted,
rewritten, or reused for an unrelated record.

Its registry record, credential, claims, reports,
or issuer keys may be revoked or superseded.
```

中文：

> Watermark ID 一经正式分配，不得被静默删除、改写或复用于无关记录；但对应的登记记录、签名凭证、权利声明、报告和 issuer key 可以被撤销或替代。

由此得到：

- 媒体中的锚点字节仍然可读取。
- resolver 可以返回 `revoked`、`superseded` 或 `conflict`。
- 历史事实保留，但当前有效性可以变化。
- 被替代记录不得静默消失。
- 新记录通过 replacement / predecessor 关系指向历史记录。

### 9.6 公理六：历史签名支持离线验证，当前状态需要新鲜信息

候选原表述：

```text
Verification must be possible without trusting HiddenShield servers.
```

审查结论：`方向接受，拆分历史验证与当前状态`

可以要求离线完成：

- 从支持的媒体中读取 Watermark ID。
- 校验 payload authentication tag。
- 匹配本地精确 SHA-256。
- 校验本地报告摘要链。
- 持有 credential、公钥 / 证书链和必要时间材料时，验证历史签名事实。

不能保证永久离线得出：

- credential 当前是否已撤销。
- issuer key 当前是否已撤销。
- 是否出现 replacement。
- 当前 rights manifest 是哪一个版本。
- registry 当前是否 active、conflict 或 superseded。
- 当前 trust policy 是否仍信任某个 Enterprise issuer。

建议冻结文案：

```text
Historical signature facts must support offline verification
when the required credential and trust material are available.

Current registry, replacement, and revocation status requires
an online resolver or a sufficiently fresh signed status list.
```

离线状态列表必须显示：

- 生成时间。
- 有效期。
- issuer。
- 签名状态。
- 数据新鲜度。
- 超期后不得继续显示当前 `active`。

### 9.7 六条公理最终状态

| 候选公理 | 最终审查状态 | 可否作为当前内部冻结原则 |
| --- | --- | --- |
| V3/39 最小锚点 | 修正后接受 | 是，冻结当前正式 profile，不宣称理论全局最优 |
| ID 只寻址 | 接受 | 是 |
| 媒体内外分层 | 修正为四层后接受 | 是 |
| auth tag 定性 | 修正术语后接受 | 是 |
| 锚点永不删除 | 修正为不删除、不复用、状态可撤销 | 是 |
| 验证脱离服务器 | 拆分历史事实与当前状态后接受 | 是 |

以上结论当前只作为内部架构待办中的评审结果，不自动成为：

- 对外标准。
- SDK 稳定 API。
- 当前生产能力。
- 商业承诺。
- 法律结论。

## 10. 内容摘要与派生关系待冻结问题

本章记录 Signed Registry Credential 设计中一个尚未冻结的关键子问题：

```text
什么对象被 digest 绑定；
如何区分精确字节、规范化内容、感知相似和派生关系；
签署 digest 到底证明了什么。
```

当前结论：

- HiddenShield 已经有正式的原文件 SHA-256、保护副本 SHA-256、验证对象摘要和报告附件摘要链。
- 当前精确摘要语义不是缺失，而是需要和未来 canonical digest、感知指纹、派生关系明确分开。
- 不允许使用一个含糊的 `contentDigest` 同时表达四种不同概念。
- 本章仅记录待冻结问题，不新增 schema、API 或算法。

### 10.1 四类内容绑定必须分离

建议未来明确区分：

```text
1. Exact Binary Digest
2. Canonical Decoded Digest
3. Perceptual Fingerprint
4. Derivation Relation
```

这四类对象的目标、确定性、验证方法和法律语义不同，不能互相替代。

### 10.2 Exact Binary Digest：当前正式主语义

建议概念模型：

```text
digestType: binary_sha256
digestScope:
  - original_file
  - protected_copy
  - verification_target
  - report_attachment
digestValue: <full sha256>
byteLength: <exact bytes>
```

语义：

> 对一份精确字节序列计算完整 SHA-256。

它可以证明：

- 当前文件是否与记录中的字节对象完全一致。
- 保护副本是否发生字节级修改。
- 报告附件是否匹配 manifest。
- write-after-read 验证针对的是哪一个保护副本。

它不能证明：

- JPG 与 PNG 表达同一视觉作品。
- 转码前后属于同一内容。
- 裁剪、resize 或重新编码后仍是同一精确对象。
- 声明人拥有版权。
- 内容真实。
- 内容不是 AI 生成。
- 法院必然采纳。

当前正式原则：

```text
binary SHA-256 binds exact bytes, not abstract creative identity.
```

### 10.3 Canonical Decoded Digest：未来可选 profile，不替代 SHA-256

未来如果存在明确业务需求，可以研究：

```text
canonical_pixels_v1
canonical_pcm_v1
canonical_video_frames_v1
```

但它们属于新协议 profile，不能覆盖或替换 `binary_sha256`。

图片 canonical profile 至少需要冻结：

- 解码器与格式容错规则。
- EXIF orientation。
- 像素尺寸。
- 色彩空间和转换矩阵。
- ICC profile。
- alpha 通道及预乘规则。
- 位深和量化。
- 动画图片帧选择。
- metadata 是否排除。
- 非法或模糊文件的拒绝规则。

音频 canonical profile 至少需要冻结：

- 解码器。
- 采样率。
- 声道数量和顺序。
- sample format。
- 浮点归一化和量化。
- delay、padding 和 encoder priming。
- 静音裁剪规则。
- metadata 是否排除。

视频 canonical profile 至少需要冻结：

- 容器和轨道选择。
- 解码器。
- 色彩空间。
- 分辨率。
- 时间基和帧时间。
- 可变帧率处理。
- 音视频轨道是否分别摘要。
- 帧采样和顺序。
- 编码 delay、rotation 和 crop metadata。

当前不建议立即冻结 canonical media profile，原因：

- 跨平台解码结果可能存在差异。
- 定义成本和 fixture 成本很高。
- 当前没有因缺少 canonical digest 而阻断的正式用户能力。
- 错误的 canonicalization 比没有 canonicalization 更容易造成错误同一性结论。

### 10.4 Perceptual Fingerprint：只用于候选检索与相似分析

感知指纹适合：

- 疑似侵权候选检索。
- 图片 resize、压缩、轻裁剪后的相似匹配。
- 视频 L2 指纹和裁剪候选窗口。
- 深度检测。
- 人工取证前的候选排序。

它不适合：

- 作为 Watermark ID。
- 替代加密 SHA-256。
- 自动证明两个作品相同。
- 自动证明派生关系。
- 自动证明版权归属。
- 自动形成法律结论。

建议未来结果模型：

```text
matchType: candidate_match
fingerprintProfile: <version>
similarityScore: <number>
thresholdProfile: <version>
matchingMethod: <method>
humanReviewRequired: true
```

禁止直接输出：

```text
same_content = true
same_owner = true
infringement_confirmed = true
```

### 10.5 Derivation Relation：显式关系，不由 hash 自动推导

以下操作通常会生成新的精确 digest：

- JPG 转 PNG。
- 音频重编码。
- 视频转码。
- resize。
- 裁剪。
- 调色。
- 加字幕。
- 混音。
- 编辑。
- 水印重写。
- registry reissue。

不能仅因为 hash 变化就自动得出：

- 这是新作品。
- 这是旧作品的合法派生。
- 这是侵权复制。
- 这是同一权利人的新版本。

未来可以考虑显式 relation type：

```text
derived_from
transcoded_from
resized_from
cropped_from
edited_from
watermark_rewritten_from
registry_reissued_from
registry_replacement_for
```

每条关系至少需要：

- source Watermark ID / record ID。
- target Watermark ID / record ID。
- relation type。
- 声明主体。
- 创建时间。
- evidence。
- 是否经过签名。
- 当前状态。

关系只是可验证声明，不自动成为法律事实。

### 10.6 `parentWatermarkUid + revision` 的边界

当前字段继续用于：

- 线性版本链。
- 用户明确选择“作为新版写入”。
- 重写 / 重签流程中的前序关系。

当前不承担：

- 所有格式转换关系。
- 任意内容 DAG。
- 多父节点合并。
- 自动版权转移。
- 自动创作贡献关系。
- 自动侵权关系。

未来如果引入 derivation graph，应使用独立 relation type，不把所有边都压缩为 `parentWatermarkUid`。

### 10.7 Digest 必须记录计算与观察来源

未来 credential 不能只记录：

```text
sha256:...
```

还需要说明：

- 谁计算了 digest。
- 谁观察到了对应文件字节。
- 使用什么绑定方法。
- 是否完成 write-after-read。
- 云端是否实际接收媒体。
- digest 是声明值还是服务端观察值。

建议概念字段：

```text
digestAlgorithm
digestScope
digestValue
byteLength
computedBy
observedBy
bindingMethod
verificationMethod
```

候选值示例：

```text
computedBy:
  - local_watermark_core
  - cloud_worker
  - external_issuer
  - user_supplied

observedBy:
  - local_device
  - hidden_shield_cloud
  - enterprise_issuer
  - not_observed

verificationMethod:
  - exact_bytes_hashed
  - write_after_read_verified
  - server_observed_bytes
  - client_asserted_digest
  - external_attestation
```

以上名称仍是设计候选，不是已冻结 schema。

### 10.8 云端签署客户端摘要的准确语义

当原始媒体未上传时，HiddenShield 云端无法合理宣称：

> 云端独立验证了原始作品内容。

准确语义应是：

> HiddenShield registry 在指定时间接收并登记了客户端提交的 digest 和相关声明。

如果客户端同时提供本地 write-after-read 结果，可以进一步表达：

> 客户端声明其使用正式 `watermark-core` 对保护副本完成了 Watermark ID 回读，并向 registry 提交了结果与摘要。

但这仍不同于：

> HiddenShield 云端亲自读取并验证了对应媒体字节。

如果未来云 worker 实际接收并处理文件，可以使用不同 `observedBy` 和 `verificationMethod`。

### 10.9 Hash 的法律与产品边界

对用户、报告、SDK 和 API 的推荐解释：

- SHA-256 是技术摘要。
- 摘要匹配证明的是精确字节一致。
- 摘要不证明权利人身份。
- 摘要不证明创作时间早于所有第三方。
- 摘要不证明作品真实。
- 摘要不证明非 AI。
- 摘要不证明使用授权合法。
- 摘要不自动证明侵权。
- TSA 可以证明某个摘要在某个可信时间点前已存在，但不自动证明权属。

签名 credential 的准确作用是：

> 证明某个 issuer 对某组规范化字段完成了签名。

它不自动证明被签字段的客观真实性，除非 credential 同时明确记录 issuer 实际观察和验证的方法。

### 10.10 内容绑定待冻结清单

恢复公共信任层设计时，必须先决定：

- Registry Credential 默认绑定原文件、保护副本还是两者。
- 是否允许只有 Watermark ID 而没有媒体 digest 的 credential。
- digest 是否必须为完整 SHA-256。
- `digestScope` 枚举。
- `computedBy`、`observedBy` 和 `verificationMethod` 枚举。

- 客户端声明 digest 与云端 observed digest 如何区分。

### 10.11 当前建议的最小冻结规则

在更完整协议恢复前，可以继续保持以下最小规则：

```text
1. 原文件 SHA-256 绑定原文件精确字节。
2. 保护副本 SHA-256 绑定保护副本精确字节。
3. 转码、裁剪、resize、编辑或重编码产生新的精确 digest。
4. 是否属于同一作品或派生版本，由显式记录关系解释，不由 hash 自动判断。
5. 感知指纹只提供候选相似结果，不替代 SHA-256。
6. 云端未观察媒体字节时，只证明登记了客户端提交的 digest。
7. Digest、签名和 TSA 均不自动构成法律权属结论。
```

## 12. 风险记录

### 12.1 长期不处理的风险

- 第三方无法仅凭公开密钥独立验证 registry 签发事实。
- 企业客户可能无法将 HiddenShield 凭证接入自己的 PKI 或审计系统。
- HMAC、数字签名、登记状态和法律结论可能继续被外部人员混淆。
- PDF、C2PA、rights manifest、许可证和 registry 可能各自演化出不兼容的 issuer/key 模型。
- 撤销语义可能在不同对象之间出现不一致。

### 12.2 过早实施的风险

- 重新打开已经完成的 V3 payload 决策，损害鲁棒性和跨端兼容。
- 在 KMS / HSM、C2PA 和企业 PKI 未对齐前锁死错误签名算法。
- 创建重复 resolver 或重复 registry，形成第二事实源。
- 在当前 RC / GA 阻断未关闭前分散发布资源。
- 把设计原型误宣传为生产信任基础设施。

## 13. 恢复条件
