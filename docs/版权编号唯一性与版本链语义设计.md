# HiddenShield 版权编号唯一性与版本链语义设计

更新时间：2026-06-27

本文档用于冻结 HiddenShield 正式版权编号的产品语义、`Watermark Payload Protocol V2`、后端优先签发与离线兜底策略、版本链规则、版权库 / 存证摘要 / 报告 / 云同步影响面和研发期数据修复口径。当前 `watermark-core` V2-119 payload、离线高熵编号、图片 / 音频 / 视频视觉容量升级、双端 Rust bridge 验证、后端 `watermark-ids` 登记 API、双端版权库字段、存证摘要、正式报告字段、同步 payload 字段、桌面端 / 移动端图片与音频写入流水线在线 `reserve -> confirm`、离线兜底、同步前自动 `confirm / reconcile`、同步仲裁 UI 和历史修复入口已完成。

重要决策：

```text
HiddenShield 仍处于研发阶段，正式写入直接进入 Watermark Payload Protocol V2。
新写入不保留 V1 payload 兼容，不在旧 32-byte payload 中做兼容式塞字段。
```

## 1. 背景与问题

用户在桌面端连续写入 3 个不同图片作品后，得到同一个版权编号：

```text
HS-747E-AF30-8178
```

这暴露了当前设计缺陷：现有 `watermarkUid` 更接近“创作者 + 设备派生的短标识”，不是“作品级版权编号”。

当前风险：

- 同一创作者、同一设备写入不同作品时，可能得到相同版权编号。
- 版权库列表、详情、存证摘要、正式报告和云同步都把 `watermarkUid` 当作主身份使用，重复编号会削弱用户对“版权编号”的理解。
- 同步冲突逻辑里存在“同 UID 不同哈希可保留为变体”的历史兼容心智，若继续沿用，会把设计缺陷包装成正常记录形态。
- 法务、报告和申诉场景里，同一个编号对应多个无版本关系的作品，会造成证据解释困难。
- 当前 32-byte payload 容量不足以完整承载 128-bit 以上记录级版权编号、父编号、版本链、摘要前缀、签发模式和更强认证标签；如果只在旧 payload 里挤字段，会把协议债务带进正式产品。

产品判断：

```text
不同作品的首次正式写入，必须生成不同版权编号。
```

因此，当前重复编号不是正确设计，而是版权编号语义与生成规则不匹配。

## 2. 第一性原则

版权编号不是创作者编号、设备编号、账号编号或本地任务编号。

版权编号代表一次正式保护副本写入后形成的可验证版权记录身份。它必须能支撑：

- 用户在版权库中区分不同作品。
- 验证页从保护副本中读出同一个编号。
- 存证摘要和正式报告围绕同一条记录解释。
- 云同步在多设备之间识别同一条记录、版本链或冲突。
- 桌面端和移动端用同一语义展示与判断。

## 3. 目标语义

### 3.1 `watermarkUid`

`watermarkUid` 是正式版权编号。

语义要求：

- 每一次新的正式首写入都应生成新的 `watermarkUid`。
- 它必须写入盲水印 payload，并能被读取端从保护副本中提取。
- 它必须进入版权库记录、存证摘要、正式报告和云同步 payload。
- 它必须由 `watermark-core` 生成或通过 `watermark-core` 的正式 payload 构造路径固化，不允许桌面端、移动端或后端各自实现。
- 它不是创作者身份的可逆编码，不应暴露设备身份、账号身份或本地路径信息。

### 3.2 `parentWatermarkUid`

`parentWatermarkUid` 表示版本链的上一版编号。

语义要求：

- 首次写入为空。
- 对已有正式水印的作品执行“作为新版写入”时，写入新的 `watermarkUid`，并把上一版编号写入 `parentWatermarkUid`。
- 它用于解释版本关系，而不是用于复用旧编号。

### 3.3 `revision`

`revision` 表示同一作品链上的版本序号。

语义要求：

- 首次写入为 `1`。
- 基于上一版写入时递增。
- `revision` 必须和 `parentWatermarkUid` 配套解释，不能单独作为唯一身份。

推荐版本链示例：

| 场景 | `watermarkUid` | `parentWatermarkUid` | `revision` |
| --- | --- | --- | --- |
| 图片 A 首次写入 | `HS-A...` | 空 | 1 |
| 图片 B 首次写入 | `HS-B...` | 空 | 1 |
| 图片 A 作为新版写入 | `HS-C...` | `HS-A...` | 2 |
| 图片 A 第三版写入 | `HS-D...` | `HS-C...` | 3 |

结论：

```text
同一作品链可以有多个版权编号；版本关系由 parentWatermarkUid + revision 解释。
```

不推荐继续让同一作品链复用同一个 `watermarkUid`，因为这会让“编号代表记录身份”与“编号代表作品根身份”混在一起，也会让不同版本的报告、保护副本哈希、可信时间和撤销 / 退款授权状态更难解释。

## 4. Watermark Payload Protocol V2

### 4.1 协议升级原则

V2 不是旧 payload 的兼容补丁，而是 HiddenShield 正式盲水印 payload 的新基础协议。

协议原则：

- 新写入只生成 V2 payload。
- V2 payload 必须完整承载至少 128-bit 的正式版权编号，不允许只把短展示编号写入水印。
- V2 payload 必须由 `watermark-core` 编码、解码、认证和生成展示编号；桌面端、移动端、后端不得自行拼装 payload。
- V2 payload 的容量必须先满足产品语义，再反向调整图片、音频和视频视觉算法容量，不允许为了保留旧算法常量而牺牲编号语义。
- V1 研发期数据不作为正式兼容目标。若本地已有 V1 试验记录，按研发期修复流程重新写入 V2 保护副本。

### 4.2 V2 逻辑字段

V2 payload 至少包含以下逻辑字段。最终二进制布局由 `watermark-core` 固化，并由合同测试锁定。

| 字段 | 建议二进制容量 | 含义 |
| --- | --- | --- |
| `magic` | 4 bytes | V2 协议魔数，和旧 payload 明确区分 |
| `protocolVersion` | 1 byte | 固定为 `2` |
| `payloadLength` | 2 bytes | 允许未来扩展，但 V2 首版固定长度 |
| `watermarkIdBytes` | 16 bytes | 128-bit 正式版权编号原始身份 |
| `parentWatermarkIdBytes` | 16 bytes | 上一版版权编号原始身份；首次写入全 0 |
| `revision` | 4 bytes | 版本次数，首次写入为 1 |
| `issuedAt` | 8 bytes | 写入时间戳 |
| `originalHashPrefix` | 至少 16 bytes | 原作品 SHA-256 摘要前缀，用于验证和同步仲裁 |
| `declarationFlags` | 至少 2 bytes | 作品声明、训练许可和授权策略等核心声明位 |
| `issueMode` | 1 byte | 后端签发、离线生成、后端确认、后端重签等状态 |
| `mediaType` | 1 byte | 图片、音频、视频音轨、视频画面等媒体类型 |
| `registryProofHash` | 至少 16 bytes | 后端预留收据或登记证明摘要；离线写入可为空值 |
| `creatorBindingHash` | 至少 16 bytes | 创作者身份绑定摘要；不得存储创作者明文 |
| `authTag` | 至少 16 bytes | payload 认证标签，必须强于旧 4-byte tag |

容量结论：

```text
V2 payload 不再以 32 bytes 为目标。`watermark-core` 已固化首版 `PAYLOAD_BYTES = 119`。
```

119 bytes 是当前实施值：它完整承载 128-bit 版权编号、128-bit 父编号、16-byte 原作品摘要前缀、16-byte registry proof hash、16-byte creator binding hash 和 16-byte auth tag。后续如果字段继续扩展，仍应优先扩展载体算法容量，而不是削弱版权编号、父编号或认证标签。

### 4.3 展示编号

`watermarkUid` 是 `watermarkIdBytes` 的展示编码。

要求：

- 展示格式继续使用 `HS-` 前缀，方便用户识别 HiddenShield 版权编号。
- 展示长度必须能代表完整 128-bit 级身份，不能再截断为 48-bit 短编号。
- 展示编号必须可由 V2 payload 中的 `watermarkIdBytes` 稳定恢复。
- 后端签发编号和离线生成编号使用同一展示规则，差异通过 `issueMode` 和登记状态解释。

建议展示形态：

```text
HS-XXXXXXXX-XXXXXXXX-XXXXXXXX-XXXXXXXX
```

每组 `XXXXXXXX` 表示 32-bit 十六进制片段，四组完整表达 128-bit 身份。最终大小写、分组和校验位由 `watermark-core` 决定。

### 4.4 算法容量升级影响面

V2 payload 扩容会直接影响 `watermark-core` 的写入和解析算法。代码实施必须把以下内容作为同一施工面处理。

图片水印：

- 更新图片主 payload bit 写入长度。
- 更新图片 sync packet，从 `4 + 32 + checksum` 扩展为 `4 + PAYLOAD_BYTES + checksum`。
- 重新评估最小可写入图片尺寸、block 数、冗余策略、纠错阈值和 alpha 参数。
- 提取路径只按 V2 sync packet 和 V2 payload 解码，不再把 V1 作为正式 fallback。

音频水印：

- 更新音频 recovery packet，从 `4 + 32 + checksum` 扩展为 `4 + PAYLOAD_BYTES + checksum`。
- 重新评估最低音频时长、每帧可承载位数、冗余倍数、恢复包偏移和容错阈值。
- 更新写入后回读和恢复包提取，确保读出完整 128-bit 编号和版本链字段。

视频视觉水印：

- 更新 DCT / sync / ECC bitstream 的 payload 位数。
- 重新计算 `PAYLOAD_BYTES * 8 * ECC_REPEAT` 对策略区域数、采样帧数、性能预算和最低分辨率的影响。
- L3 当前仍属于 staged / 内部测试能力；V2 改造只表示核心协议同源，不改变当前用户可承诺边界。

服务 API：

- `encode_payload` / `decode_payload` 应升级为 V2 语义，或显式命名为 `encode_payload_v2` / `decode_payload_v2` 后再替换正式调用点。
- `WatermarkPayload` 结构体不再围绕 `user_seed + device_id` 建模，而应围绕记录级版权编号、父编号、版本链、摘要和签发状态建模。
- 写入后验证必须校验完整 V2 payload，而不只是比较展示编号。

### 4.5 研发期旧数据处理

由于产品未正式上线，V1 不作为正式兼容目标。

研发期处理口径：

- 新代码不再生成 V1 payload。
- 新 QA fixture 和跨端互验样本全部重建为 V2。
- 本地已有旧实验记录可以被标记为 `dev_legacy_payload`，但不进入正式报告、商业化验收和发布门禁。
- 如果需要保留旧样本用于算法对照，应放在内部测试目录，不作为用户数据迁移承诺。
- 开发者或测试用户需要继续验证旧文件时，应重新选择原作品并生成 V2 保护副本。

## 5. 编号签发策略：后端优先，离线兜底

HiddenShield 的正式版权编号应成为客户端与后端版权登记能力打通的入口。

目标策略：

```text
在线默认路径：后端签发 / 确认唯一版权编号
离线兜底路径：本地高熵签发临时正式可写编号，联网后补登记
```

### 5.1 在线默认路径

当客户端可访问 HiddenShield 后端时，桌面端和移动端应在正式写入前向后端申请或确认版权编号。当前桌面端与原生移动端图片 / 音频写入已按此路径实施：写入前调用 `reserve`，使用后端返回的 `watermarkUid` 与 `registryProofHash` 构造 V2 payload，写入后通过 `confirm` 上报原作品摘要、保护副本摘要和写入后验证状态。

建议后端契约：

- `POST /v1/watermark-ids/reserve`
- 输入：创作者档案 ID、设备 ID、媒体类型、原作品摘要、保护副本计划摘要、父编号、版本次数、客户端生成的请求幂等 ID。
- 输出：`watermarkUid`、`registryId`、`issueMode=server_reserved`、`expiresAt`、服务端签名或登记收据。
- 幂等：同一 `requestId` 重试必须返回同一编号。
- 隐私：不得上传原始媒体、保护副本、本地路径或可还原内容；只上传元数据和摘要。

后端职责：

- 确保新签发 `watermarkUid` 在全局登记库中唯一。
- 记录 `watermarkUid -> originalHash / creatorProfile / account / device / parentWatermarkUid / revision` 的登记关系。
- 对同一作品链的新版写入返回新 `watermarkUid`，并保留父编号链路。
- 支持后续云同步、正式报告、单份报告购买、团队版权库和商业化审计。

客户端职责：

- 优先使用后端返回的 `watermarkUid` 构造 payload。
- 写入失败或用户取消时，后端预留编号应可过期释放或标记为未使用。
- 写入成功后上报最终登记确认：原作品摘要、保护副本摘要、写入后验证状态、可信时间状态。

### 5.2 离线兜底路径

当未联网、后端不可用、云地址未配置或用户选择本地离线使用时，桌面端和移动端仍必须允许图片 / 音频正式写入。

离线编号生成要求：

- 使用操作系统 CSPRNG 生成至少 128-bit 随机记录身份，或使用 UUIDv7 / ULID 等具备足够熵的标准身份。
- 在本机版权库落库前做本地重复检查；若发现重复，重新生成并重试。
- 编号展示仍保持 `HS-...` 前缀，但展示长度必须足以支撑低碰撞概率；不应继续只用 48-bit 甚至更短的创作者 / 设备派生片段作为作品编号。
- `watermark-core` payload 内部应保留足够完整的记录身份，展示编号可以是该身份的编码或校验后的短格式。
- 编号生成不得包含原始媒体路径、本地路径、真实设备序列号、账号明文或其他隐私信息。

离线编号状态：

| 状态 | 含义 | 用户可见表达 |
| --- | --- | --- |
| `server_reserved` | 后端已签发并登记 | 已登记 |
| `offline_generated` | 本机高熵生成，尚未与后端登记 | 本地生成，待联网登记 |
| `server_confirmed` | 离线编号联网后经后端确认唯一 | 已登记 |
| `server_reissued` | 后端发现需要换号并重新签发 | 已重新登记 |

当前实施口径：

- 桌面端和移动端任何 `reserve / confirm` 网络失败、后端不可用、账号资料缺失或云地址未配置，都不会阻断本地图片 / 音频写入。
- 离线写入仍由 `watermark-core` V2 构造路径使用 128-bit CSPRNG 编号，落库为 `offline_generated + pending_registration`。
- 云同步发送前会对 `pending_registration` 记录调用 `reconcile`，对 `server_reserved / reserved` 记录调用 `confirm`；成功后回写本地版权库和同步 payload。

离线可接受的唯一性定义：

```text
在无云服务、无中心分配的前提下，通过高熵随机身份 + 本地重复检查，将碰撞概率降到工程上可忽略；联网后由后端登记确认或重新签发。
```

不可接受的定义：

- 只根据创作者身份生成。
- 只根据设备身份生成。
- 只根据创作者 + 设备生成。
- 只根据文件名或本地路径生成。
- 为了确定性而让同一创作者 / 设备的不同作品复用同一编号。

### 5.3 后端重新签发

当后端发现离线编号与已有登记冲突，或发现旧模型重复编号，不能只把问题展示给用户后结束。系统必须进入重新签发和修复流程。

重新签发原则：

- 若原始媒体或保护副本可访问，客户端应自动或半自动生成新的保护副本，把新 `watermarkUid` 写入 payload，同时把旧 `watermarkUid` 写入 `parentWatermarkUid`，并更新版权库记录。
- 若媒体不可访问，版权库记录进入 `reissue_required`，并在用户重新选择原作品或保护副本后完成修复。
- 不允许只在 UI 上提示“旧模型”而不提供系统级修复路径。
- 不允许只改版权库字段而不改保护副本 payload；否则验证页读出的编号会和版权库不一致。

## 6. 云同步与登记一致性

新模型实施后，云同步不把“同 `watermarkUid` + 不同原作品哈希 + 无版本链关系”直接作为普通变体，也不把它直接做成用户需要理解的硬冲突。默认策略是交给后端登记库仲裁。

同步合并规则调整为：

| 条件 | 解释 | 处理 |
| --- | --- | --- |
| 同 `watermarkUid`、同原作品哈希、同保护副本摘要 | 同一记录重复同步 | 幂等合并 |
| 同 `watermarkUid`、同原作品哈希、更高 `revision` 且父链成立 | 同一作品链升级 | 记录版本链 |
| 不同 `watermarkUid`、`parentWatermarkUid` 指向上一版 | 正常新版写入 | 作为版本链展示 |
| 同 `watermarkUid`、不同原作品哈希、无父链关系，且后端在线 | 登记异常 / 离线碰撞 / 历史重复 | 后端重新签发或生成 alias repair 任务，不作为普通变体静默合并 |
| 同 `watermarkUid`、不同原作品哈希、无父链关系，且后端离线 | 待登记仲裁 | 本地保留两条记录，标记 `pending_registry_reconcile`，不覆盖彼此 |
| 同 `watermarkUid`、不同保护副本摘要、同原作品哈希 | 可能是重新导出或同作品修复 | 交给登记库确认，不能覆盖可信字段 |

云端和客户端都必须保留仲裁证据：

- 本地记录来源。
- 远端记录来源。
- 原作品摘要。
- 保护副本摘要。
- 写入时间。
- 可信时间状态。
- 父编号与版本次数。
- 编号签发模式：后端签发 / 离线生成 / 后端确认 / 后端重签。

## 7. 版权库、存证摘要和报告字段

版权库记录必须持久化：

- `watermarkUid`
- `watermarkIdBytes` 或其不可逆等价编码
- `payloadProtocolVersion`
- `payloadBytesLength`
- `parentWatermarkUid`
- `parentWatermarkIdBytes` 或其不可逆等价编码
- `revision`
- `originalHash`
- `protectedCopyHash`
- `protectedCopyName`
- `outputStrategy`
- `writeVerificationStatus`

- `thirdPartyVerificationStatus`

- `watermarkIdIssueMode`

- `payloadAuthStatus`

存证摘要必须展示：

1. 版权编号：`watermarkUid`
2. 版本次数：`revision`
3. 上一版编号：`parentWatermarkUid`，首次写入显示“无”
4. 原作品指纹
5. 保护副本摘要
6. 完成后验证状态
7. 可信时间 / 第三方验证状态

正式报告必须解释：

- 版权编号代表本次正式保护副本写入形成的记录身份。
- 上一版编号和版本次数用于解释版本链。
- 原作品指纹与保护副本摘要用于区分不同作品和不同保护副本。
- 用户声明字段是创作者声明，不是系统自动鉴定。

## 8. 研发期旧数据修复口径

已存在重复 `watermarkUid` 的研发期记录不能只提示旧模型后结束，也不能只改版权库字段。因为旧保护副本内嵌的 payload 仍会读出旧编号，单改数据库会破坏验证一致性。

修复原则：

- 自动扫描本地版权库中同 `watermarkUid`、不同原作品哈希且无父链的研发期记录。
- 对可访问原始媒体或保护副本的记录，进入自动修复队列：向后端申请新编号或生成离线高熵编号，重新生成 V2 保护副本，写入 V2 payload，更新版权库记录。
- 对不可访问媒体的记录，标记为 `reissue_required`，并在用户重新选择文件后继续修复。
- 后端在线时，旧重复编号可登记为研发期 alias，方便内部排查，但新报告和新同步记录应指向修复后的 V2 编号。
- 正式报告默认不导出未修复的重复编号记录；如果用户强制导出基础摘要，必须显示“待重新登记”。
- 云同步不把历史重复记录静默合并为普通变体，必须走登记仲裁或修复队列。

历史记录用户可见建议：

```text
该记录使用研发期旧版 payload 生成，正在等待重新登记。HiddenShield 会在可访问原作品或保护副本后重新签发编号并生成 V2 保护副本。
```

## 9. 双端一致性要求

桌面端和移动端必须同时实施：

- 同一 `Watermark Payload Protocol V2` 编码、解码、认证和编号生成规则。
- 同一版本链判断。
- 同一版权库字段。
- 同一存证摘要字段顺序。
- 同一报告解释口径。
- 同一同步冲突规则。
- 同一历史记录修复状态。

禁止出现：

- 桌面端生成 V2 payload，移动端仍生成旧 32-byte payload。
- 移动端只展示 `revision`，但不保存 `parentWatermarkUid`。
- 云同步把桌面端重复编号静默合并，但移动端进入重新登记。
- 报告端解释为“作品唯一编号”，验证端解释为“创作者设备编号”。

## 12. 已确认决策

已确认：

1. 接受“同一作品新版写入也生成新版权编号”。
2. 不接受历史重复编号只提示旧模型；必须提供重新签发、重新生成保护副本和后端登记修复路径。
3. 不接受把“同 UID 不同原作品哈希且无父链”简单收紧成用户侧冲突；默认交给后端登记库仲裁，后端不可用时进入待登记仲裁状态。
4. 新版权编号默认由后端签发 / 确认唯一，以打通用户端与后端版权登记、商业化和未来团队版权库能力。
5. 后端不可用、未联网或云服务未配置时，桌面端和移动端仍可本地运行，使用系统安全随机数生成至少 128-bit 高熵编号，现实上可视为唯一，并在联网后补登记。
6. 不接受兼容式升级。由于产品仍处于研发阶段，正式写入直接切换到 `Watermark Payload Protocol V2`，不在旧 32-byte payload 中塞 V2 字段，不把 V1 作为新产品兼容目标。

最终语义：

```text
Watermark Payload Protocol V2 完整承载记录级版权编号；在线优先后端唯一编号；离线高熵本地编号兜底；版本链通过 parentWatermarkUid + revision 表达；联网后由后端登记库确认、仲裁或重新签发。
```

当前 V2 payload 最终二进制布局、`PAYLOAD_BYTES = 119` 常量、图片 / 音频 / 视频视觉容量预算已经在 `watermark-core` 落地并通过测试；后端 `reserve / confirm / reconcile / reissue` API、双端编号签发状态落库、摘要、报告字段、同步 payload 字段、双端图片 / 音频写入流水线在线优先 `reserve -> confirm` 和同步前自动 `confirm / reconcile` 已完成。下一步进入运行态 QA、云同步登记仲裁 UI 和历史重复编号修复队列。
