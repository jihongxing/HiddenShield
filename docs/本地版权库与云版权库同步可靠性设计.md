# 本地版权库与云版权库同步可靠性设计

更新时间：2026-07-03

本文用于收口 HiddenShield 本地版权库与云版权库的正式同步任务。它补充 `docs/商业化落地Roadmap.md`、`docs/双端能力一致性Roadmap.md` 和 `docs/用户体系与登录注册体系规划.md`：云同步不能只停留在字段契约完成，必须达到真实运行态可恢复、可解释、可验收。

## 1. 背景与当前问题

本轮桌面端真实 QA 发现：

- 本地 `cloud_sync_profile.json` 可显示 Creator / `cloud_sync=true`，但后端 `GET /v1/me` 对同一账号返回 Free / `cloud_sync=false` / `syncPolicy=blocked_by_entitlement`。
- 新版权记录成功入本地库后进入 `cloud_sync_queue.pending`，但 `attempts=0`，说明没有真正触发上传。
- 后端 `cloud_sync_events` 没有对应记录，证明这不是上传失败，而是未进入云同步请求。
- 本地旧队列存在长时间停留在 `syncing` 的记录，当前恢复逻辑只重置 `failed`，不会恢复 stale `syncing`。
- 手动使用最新有效 token 推送时，后端按真实权益返回 403，证明后端门禁正确，本地权益快照陈旧会误导 UI。

因此本任务的目标不是单点修复按钮，而是把“权益单一事实源 + 同步状态机 + 自动触发 + 恢复策略 + 双端验收”作为一个完整系统设计。

## 1.1 PostgreSQL 迁移后的重新审计结论

审计日期：2026-07-03

本文最初创建时，`feedback-backend` 仍可被近似理解为单一 SQLite 云后端。现在项目已经完成 `docs/云版权库PostgreSQL迁移设计.md` 的 P1-P4 本机可验证切片：后端已有 SQLite dev/test adapter、feature-gated PostgreSQL repository adapter、真实 migration 文件、P3.4 聚合 runtime QA 和 P4 SQLite fixture -> disposable PostgreSQL 导入 smoke；但 P5 生产压测 / 备份恢复 / observability / 切换 runbook / release owner 签字仍是 BLOCKED，正式 UI / mock / release 默认路径未切 PostgreSQL。

所以本设计需要按三层重新表述：

| 层级 | 当前真实状态 | 对同步可靠性任务的影响 |
| --- | --- | --- |
| 端侧本地版权库 / 队列 SQLite | 桌面端和移动端仍使用本地 SQLite / 本地 store 保存 vault、队列、离线缓存 | S0/S1 的主战场仍是端侧：远端权益快照覆盖本地缓存、stale `syncing` 恢复、自动 flush 触发和诊断文案。 |
| `feedback-backend` SQLite dev/test adapter | 仍是本地开发、RC1 无外部依赖和默认 `cloud:backend` 路径 | `cloud:sync-reliability-contract` 必须先保证 SQLite adapter 当前合同不退。 |
| `feedback-backend` PostgreSQL adapter | auth / sync / registry 首批 repository 已有 disposable runtime QA，但未切默认路径；生产 readiness BLOCKED | 新增同步可靠性能力不能只改 SQLite 路径；任何后端语义变更都必须同步检查 Postgres migration / adapter / runtime QA，或明确标为 Postgres blocked。 |

审计判断：

- 原始问题仍成立：本地 Creator 缓存与后端 Free 快照冲突、新记录 `pending / attempts=0`、旧 `syncing` 不恢复，仍是 RC1 云同步可靠性 blocker。
- “后端是唯一会员权益事实源”的原则更重要：PostgreSQL 迁移后，端侧不能把本地 profile 当作正式门禁，也不能把 SQLite dev/test 的 fixture 状态误认为生产权益。
- 当前 `cloud_sync_events` 的 SQLite schema 与 PostgreSQL migration 都仍以 `account_id + device_id + client_event_id` 幂等为核心，尚未持久化 `payload_hash`、`entity_revision` 或 per-event ingestion result；因此 S0/S1 不能宣称已经解决“同 clientEventId payload 变化”问题，S3 必须升级为后端双 adapter 合同任务。
- PostgreSQL `cloud_sync_events.sequence` 使用 `BIGSERIAL`。P3.2 为重复 `client_event_id` 做了显式 pre-check，避免普通重复事件造成可见 cursor 跳号；后续可靠性合同必须继续覆盖 SQLite 与 PostgreSQL 两条路径的重复 flush 不新增事件、不推进可见 cursor。
- P5/P6 未通过前，本文不得把“云版权库生产 PostgreSQL SLA”或“Enterprise API 生产同步能力”写成已完成；只能说本地 / disposable / RC1 无外部依赖范围可验证。

审计后的执行原则：

- S0/S1 继续推进，但范围限定为端侧事实源刷新、队列恢复、自动触发和 SQLite dev/test 后端合同，不依赖生产 PostgreSQL。
- PostgreSQL 只纳入合同令牌和后续 optional smoke，不作为 S0/S1 的生产前提，也不因 disposable runtime QA 通过而切换正式 UI / mock / release 默认路径。
- 任何触及 `cloud_sync_events` schema、batch 返回结构、payload hash、entity revision、云端投影表或 ingestion results 的工作，必须同时更新 `docs/云版权库PostgreSQL迁移设计.md`，并复跑 `cloud:db-portability-contract`、`cloud:postgres-runtime-qa` 或建立明确 blocked artifact。
- `cloud:sync-reliability-contract` 应拆成两层：默认无外部依赖层覆盖端侧 / SQLite dev adapter；可选 Postgres 层复用 disposable Postgres，覆盖相同幂等、cursor、Free 403 和未来 payload hash 语义。

## 2. 目标

### 必须达成

- 会员权益只有一个正式事实源：后端账户快照。
- 本地权益只允许作为离线缓存，不允许在联网成功后覆盖后端事实。
- Creator / Studio / Enterprise 且 `cloud_sync=true`、`syncPolicy=auto_cloud_vault` 时，新版权记录必须自动进入 pull / flush / pull 流程。
- Free 或后端返回 `blocked_by_entitlement` 时，UI 必须显示“当前账号无云同步权益”，不得继续显示 Creator 可同步。
- 队列状态必须可恢复：应用重启、网络中断、进程崩溃、token 轮换、后端 401 / 403 / 429 / 5xx 都要进入明确状态。
- 云同步不得上传原始媒体、保护副本文件、本地路径或可还原媒体内容。
- 双端行为一致：桌面端与移动端使用同一同步策略、同一权益快照语义、同一失败文案和同一验收门禁。

### 不在本轮做

- 不改变水印 payload、版权编号格式或 `watermark-core` 算法。
- 不同步媒体文件本体。
- 不放宽 Free 云同步权益。
- 不引入团队共享版权库的多成员冲突编辑语义；团队空间仍按后续 Studio / Enterprise 任务推进。

## 3. 单一会员权益来源

### 原则

后端是正式会员权益事实源。本地保存的 `DesktopCloudSyncProfile` / 移动端 `SyncProfile` 只能是缓存，必须带有来源和新鲜度语义。

建议将端侧权益读取改为三层：

| 层级 | 用途 | 是否可做正式门禁 |
| --- | --- | --- |
| `remoteEntitlementSnapshot` | 来自 `auth/sessions`、`auth/refresh`、`GET /v1/me`、`GET /v1/entitlements/current` | 是 |
| `cachedEntitlementSnapshot` | 最近一次成功远端快照，本地离线展示 | 仅可离线提示，不可在联网成功后覆盖远端 |
| `localFallbackEntitlement` | 未登录 / 后端不可用时的本地 Free 能力 | 只能放行本地写入，不能放行云同步 |

### 端侧规则

- 启动后如果存在登录 profile，先显示缓存状态，但后台必须立即刷新 `GET /v1/me` 或 refresh。
- 刷新成功后，以后端返回的 `entitlement.features.cloud_sync` 和 `syncPolicy` 覆盖本地缓存。
- 刷新返回 Free / blocked 时，必须停止自动 flush，把队列保留为 `blocked_by_entitlement` 或 pending-with-blocker，并更新 UI。
- refresh 成功会轮换 access token 和 refresh token，端侧必须原子写回 profile；否则旧 token 会造成后续 401。
- 401 不直接清空本地版权库；先尝试 refresh，一次成功后继续原请求，一次失败后进入 `auth_required`。
- 403 不重试为网络错误；标记为 `blocked_by_entitlement`，提示刷新权益或升级。

## 4. 同步数据边界

云版权库只保存白名单 metadata：

- 版权记录基础字段：`watermarkUid`、媒体类型、文件名 / 标题、创建时间、创作者档案、版本链。
- 摘要字段：原作品 hash、保护副本名称、保护副本 hash、输出策略。
- 登记字段：签发模式、registry status / receipt、payload protocol、payload bytes、payload auth status。
- 验证字段：写入后验证状态、验证说明、验证时间。
- 声明字段：作品来源、训练许可、创作方式、人工编辑程度、真实性声明、自定义版权声明。
- 报告授权字段：单份报告购买 / 退款撤销 / Creator 报告权益摘要。
- L2 / L3 metadata：仅不可逆 notary / receipt / 自检摘要，不保存对象 ref、签名 URL、本地路径或媒体字节。

禁止同步：

- 原始媒体。
- 加水印保护副本媒体。
- 本地路径。
- creator seed 明文。
- 可还原媒体内容的完整数据。

## 5. 本地队列状态机

建议将 `cloud_sync_queue.status` 从当前的 `pending / syncing / failed / synced` 扩展为可诊断状态：

| 状态 | 含义 | 自动恢复 |
| --- | --- | --- |
| `pending` | 等待发送 | 是 |
| `syncing` | 当前进程正在发送 | 超过 lease TTL 后恢复 |
| `synced` | 云端已接受 | 否 |
| `failed_retryable` | 网络 / 5xx / 429 / 临时 registry 错误 | 退避后重试 |
| `failed_terminal` | payload 无效、记录缺失、schema 不兼容 | 否，需要修复 |
| `blocked_by_entitlement` | 后端返回 403 或权益快照无 `cloud_sync` | 权益恢复后重置为 pending |
| `auth_required` | refresh 失败或设备撤销 | 重新登录后重置为 pending |
| `paused_by_user` | 当前设备 syncPolicy 为 `manual_local_only` | 用户恢复后重置为 pending |

如果暂不做 schema 大迁移，也必须先实现兼容方案：

- 新增 `last_error_code`、`lease_until`、`blocked_reason`、`last_http_status`。
- 将旧 `failed` 通过 `last_error_code` 区分 retryable / terminal / entitlement / auth。
- 启动和手动同步前恢复 stale `syncing`：`status='syncing' AND updated_at < now - lease_ttl` 转回 `pending`，保留 attempts。

## 6. 增量同步原则

云同步必须是增量同步，不能每次全量上传本地版权库。

### Push 增量

- 本地已经同步成功的队列项必须保持 `synced`，下次 flush 不再发送。
- flush 只读取以下队列项：
  - `pending`。
  - 到达重试时间的 `failed_retryable`。
  - lease 超时后恢复的 stale `syncing`。
  - 权益恢复、重新登录或用户恢复自动同步后被显式转回 `pending` 的记录。
- 新增版权记录、登记状态变化、报告授权变化、L2 notary / L3 receipt metadata 变化时，才创建或更新对应队列事件。
- 如果一条已 `synced` 的版权记录后续 metadata 变化，必须生成新的 `eventRevision` / `clientEventId`，或以 `payloadHash` 证明这是新版本事件；不能复用旧 `synced` 事件导致云端 `INSERT OR IGNORE` 静默吞掉更新。
- 批量 flush 是“待同步事件批量”，不是“本地版权库全量批量”。

### Pull 增量

- 客户端必须保存 `lastRemoteCursor`。
- pull 请求默认携带 cursor，只拉取 cursor 之后的云端变更。
- 只有 pull 成功并完成本地合并后，才能推进本地 cursor。
- cursor 丢失、账号切换、workspace 切换或本地库重建时，才允许从空 cursor 做一次全量增量初始化。
- pull 到的云端事件也要按 `clientEventId` / `entityRevision` / `payloadHash` 去重，不能重复插入本地版权库。

### 同步过的记录如何避免重传

当前桌面端已有 `cloud_sync_queue.status='synced'` 语义，后续实现必须继续保证：

- `list_pending_cloud_sync_queue` 不返回 `synced`。
- 手动同步按钮不重置 `synced`。
- 启动恢复不重置 `synced`。
- 只有记录实际发生新 metadata 变化时，才创建新事件。

验收：同一条已经同步成功的版权记录，连续执行 3 次自动 flush 和 3 次手动 flush，后端 `cloud_sync_events` 不新增重复事件；如果该记录的 registry receipt 或报告授权状态变化，则只新增 1 条新 revision 事件。

## 7. 自动触发策略

自动同步触发点必须统一：

- 登录成功：`pull -> recoverStale -> flush -> pull`。
- refresh 成功：`recoverStale -> flush -> pull`。
- `GET /v1/me` 确认 `auto_cloud_vault`：`recoverStale -> flush -> pull`。
- 新版权记录入库：只 enqueue 该新增记录事件；如果当前远端快照允许云同步，触发后台 debounce flush。
- 版权编号登记状态变化：enqueue 最新 payload，并触发 debounce flush。
- 报告购买授权状态变化：enqueue，并触发 debounce flush。
- 应用启动：先 refresh / me，再按远端 `syncPolicy` 决定是否自动 flush。
- 应用恢复前台：如果距离上次同步超过阈值，执行一次轻量 `pull -> flush -> pull`。
- 网络从不可用恢复：执行 `recoverStale -> flush`。
- 用户手动点击“同步待处理记录”：先刷新快照，再 recover stale，再 flush；不要直接相信旧 profile。

建议 debounce：

- 新增记录后 1 到 3 秒触发一次 flush。
- 同一进程同时只能有一个 flush worker。
- 多次触发合并为一次，避免连续写入批量素材时打爆后端。

## 8. 断线续传与失败恢复

本项目首期同步的是 metadata，不是媒体大文件，因此“断线续传”的核心是队列续传、游标续拉和幂等重放。

### Push 续传

- 每条事件必须有稳定 `clientEventId`，当前 `desktop-vault-{recordId}-{revision}` 可继续使用，但应确保同一记录 payload 更新时不会被云端旧 `INSERT OR IGNORE` 吞掉。
- 建议增加 `eventRevision` 或 `payloadHash`，当同一 `clientEventId` payload 改变时，后端要能识别是幂等重复还是新版 metadata。
- push batch 以小批量提交，默认 20 到 50 条。
- 每个 batch 成功后只把 accepted ids 标为 `synced`；未返回 accepted 的记录必须进入 retryable failed。
- 进程崩溃在 `syncing` 后、HTTP 返回前发生时，下一次启动通过 lease TTL 恢复。

### Pull 续拉

- 客户端保存 `lastRemoteCursor`，pull 成功后才写 cursor。
- pull 应支持空 cursor 全量增量读取。
- pull 合并时不写入本地路径和媒体字节。
- pull 与 flush 顺序默认 `pull -> flush -> pull`，避免先上传旧本地状态覆盖另一端新状态。

### Token 恢复

- 401：自动 refresh 一次并重放当前请求。
- refresh 成功：原子保存新 token，再继续 flush。
- refresh 失败：队列标记 `auth_required`，UI 提示重新登录。
- 设备撤销：清 token，保留本地队列和本地版权库。

## 9. 去重与冲突策略

### 本地去重

- 同一 `record_id + revision + operation` 只保留一个待发送事件。
- 如果记录 payload 更新，更新队列中的 `event_json` 和 `payload_hash`。
- `synced` 记录再次发生登记 / 报告授权 / L2 notary / L3 receipt 字段变化时，必须生成新的 revision 或新的 `clientEventId`，不能因为旧事件已 synced 而吞掉更新。
- 没有 metadata 变化的 `synced` 记录不得再次入队，不得通过“全量重扫本地库”重复发送。

### 云端去重

- 后端继续以 `account_id + client_event_id` 做幂等。
- 后端应额外保存 `payload_hash` 和 `entity_revision`：
  - 相同 `client_event_id + payload_hash`：幂等接受。
  - 相同 `client_event_id` 但 payload hash 变更：返回冲突或接受为新版，不能静默忽略。
- 云端版权库投影应以 `watermarkUid + revision` 为核心身份，兼容端侧 `record_id` 只作为本机引用。

### 冲突处理

- 同一 `watermarkUid + revision`、不同 hash 且无父链：进入 registry 仲裁 / reissue 流程。
- 同一字段双端同时更新：按字段类型处理。
- 服务器确认字段优先于本地缓存字段，例如 entitlement、registry receipt、report grant。
- 用户声明字段可使用 last-write-wins，但必须保留 `sourceDevice`、`updatedAt` 和审计事件。

## 10. 同步限流策略

### 客户端限流

- 单设备同时最多一个 push worker、一个 pull worker。
- push batch 默认 50 条，上限 100 条。
- 失败重试使用指数退避：30 秒、2 分钟、10 分钟、30 分钟、2 小时。
- 429 使用后端 `Retry-After`，没有则按 10 分钟。
- 前台手动同步可绕过退避一次，但不能绕过 403 / auth_required / terminal failed。
- 批量写入期间只 enqueue，不逐条立即发请求；由 debounce worker 批量发送。

### 后端限流

- 对 `sync/events:batch` 按 account + device 限流。
- 单 batch events 上限固定，超过返回 400。
- 每条 event payload 大小上限固定，超限返回 terminal error。
- 对匿名 / 未认证请求直接 401；对 Free 同步 push / pull 返回 403。

## 11. UI 与诊断

版权库同步状态必须从“队列摘要”升级为“原因摘要”：

- `正在自动同步`：远端快照 `cloud_sync=true` 且 `auto_cloud_vault`。
- `等待上传`：有 pending，后台 worker 尚未完成。
- `同步受阻：账号无云同步权益`：后端返回 Free / 403。
- `同步受阻：需要重新登录`：refresh 失败或设备撤销。
- `自动同步已暂停`：`manual_local_only`。
- `部分记录等待重试`：retryable failed 且有 next retry。
- `部分记录需要修复`：terminal failed。

诊断信息必须包含：

- account id / workspace id / device id。
- 本地缓存权益和远端最新权益的差异。
- syncPolicy。
- pending / syncing / retryable / blocked / auth_required / terminal / synced 计数。
- last attempt / last success / last failure / next retry。
- 最近 HTTP status 和 error code。

## 12. 双端实现切面

### 桌面端

- `get_desktop_cloud_sync_profile` 返回缓存，但 UI 同时应有远端刷新状态。
- `flush_desktop_cloud_sync_queue` 入口先刷新或校验远端快照。
- pipeline 成功入队后触发后台 auto sync worker。
- 启动时恢复 stale `syncing`。
- token refresh 成功必须保存新 token，再继续原请求。

### 移动端

- 移动端 `SyncProfile` 同样只作为缓存。
- 登录、refresh、权益刷新、前台恢复、新记录入库后执行同一触发策略。
- 移动端只同步 metadata，不上传本地路径或媒体字节。
- 移动端 L2 / L3 metadata 入库后也走同一队列策略。

### 后端

- `auth/sessions`、`auth/refresh`、`me`、`entitlements/current` 返回同一权益事实。
- `sync/events:batch` 返回结构化 per-event 结果，至少能区分 accepted / rejected / duplicate / conflict。
- Free push / pull 明确 403。
- 记录 payload hash、entity revision 和 source device，避免静默吞掉新版 payload。

## 13. 验收门禁

新增或扩展以下自动化门禁：

1. `cloud:sync-reliability-contract`
   - 本地 Creator 缓存 + 后端 Free 时，端侧刷新后必须以后端 Free 为准。
   - access token 401 后 refresh 成功，必须保存新 token 并继续 flush。
   - refresh 失败进入 `auth_required`。
   - 403 进入 `blocked_by_entitlement`，不做网络重试。
   - stale `syncing` 启动后恢复为 pending 或 retryable。
   - 已 `synced` 队列项连续 flush 不重复上传；只有 metadata 变化才新增 revision 事件。
   - 默认模式使用无外部依赖 / SQLite dev adapter；不得要求生产 PostgreSQL。
   - 合同必须检查本地 Creator 缓存不可覆盖远端 Free 快照，并检查 UI / 队列诊断口径不再只显示“等待上传”。

2. `cloud:sync-reliability-postgres-smoke`
   - 可选 disposable PostgreSQL 层，复用 `cloud:postgres-runtime-qa` 的安全边界。
   - 覆盖 Free 403、Creator push / pull、重复 `client_event_id` 幂等、重复 flush 不推进可见 cursor。
   - 在 `payload_hash` / `entity_revision` 尚未落地前，必须明确输出 `payload_hash_not_implemented`，不能伪造成已完成。
   - 该门禁通过前，不得把同步可靠性修复宣称为 PostgreSQL 生产 ready。

3. `cloud:sync-runtime-qa`
   - 启动临时后端，创建同账号 desktop / mobile 两设备。
   - Creator 写入图片 / 音频 metadata 后自动同步到另一端。
   - Free 写入后本地入库，但云同步被 403 阻断且 UI 状态正确。
   - 断网写入后恢复网络，pending 自动 flush。
   - 批量 20 条记录只触发有限 batch 请求。

4. `dual:contract` 扩展
   - 检查双端同步状态文案一致。
   - 检查双端不把本地 cached entitlement 当正式云同步门禁。
   - 检查同步 payload 不含本地路径、媒体字节、对象 ref、签名 URL。

5. `commercial:ci` 接入
   - 在 RC1 前把 `cloud:sync-reliability-contract` 纳入商业化总门禁。
   - 不默认接入 Postgres smoke，除非本机 disposable Postgres 环境可用；生产 readiness 仍由 PostgreSQL P5/P6 gate 控制。
