# HiddenShield 面向司法使用场景的版权证据报告 PDF 升级规划

更新时间：2026-07-14

## 1. 规划结论

HiddenShield 不应只把现有 Markdown 报告“打印成 PDF”，而应把报告产品升级为一套可读、可验、可追溯的证据交付物：

1. **PDF 主报告**：供创作者、律师、平台申诉人员和争议处理人员快速阅读。
2. **JSON 机器附件**：保留完整结构化字段，作为 PDF 内容的机器可读事实源。
3. **证据清单 Manifest**：列出包内每个文件、字节数、SHA-256、生成时间和相互引用关系。
4. **校验入口**：通过报告编号、二维码或本地校验工具验证报告与附件是否被修改。
5. **可选证据附件**：TSA token、registry receipt、视频存证收据、验证日志等已有材料。

首版产品名称建议使用：

> **HiddenShield 版权证据技术报告**

不要直接使用“司法鉴定报告”“法院认可报告”“司法级报告”作为对外名称。当前产品可以朝司法使用场景设计，但报告仍是技术系统生成的辅助证据材料，不替代司法鉴定、公证、律师法律意见或法院对证据的最终认定。

## 2. 产品目标

### 2.1 用户目标

- 用户能在 30 秒内理解作品、权利声明、保护记录和验证结论。
- 用户能把报告直接提供给平台申诉、律师咨询、调解、仲裁或诉讼材料整理流程。
- 接收方不安装 HiddenShield，也能阅读核心事实和校验报告完整性。
- 专业接收方可以继续检查 JSON、摘要值、时间材料、版本链和验证过程。

### 2.2 证据目标

报告应围绕电子数据常见审查维度组织，而不是围绕数据库字段堆叠：

- **主体关联**：记录是谁创建、声明主体是谁、主体信息来自哪里。
- **对象同一性**：原始文件摘要、保护副本摘要、媒体特征和版权编号如何对应。
- **时间关联**：本地生成时间、网络时间、TSA 时间和云端收据时间分别是什么。
- **过程可解释**：写入、读取、验证、改写、同步和报告生成经过了什么步骤。
- **内容完整性**：报告和附件是否可通过摘要、签名或可信时间材料检测篡改。
- **系统可靠性说明**：应用版本、核心协议版本、算法角色、验证状态和限制。
- **权利声明边界**：哪些信息是用户声明，哪些是系统计算，哪些是第三方返回。

### 2.3 商业目标

- 将 Creator 的“正式报告导出”从文件格式权益升级为持续可感知的专业价值。
- 将 Free 单份版权详细报告与维权证据包形成清晰差异。
- 为 Studio 后续团队报告、案件协作和审计留出结构。
- 为 Enterprise 后续 API 校验、批量证据交付和合规归档留出稳定 schema。

## 3. 三层成熟度模型

### L1：版权证据技术报告 PDF

当前最适合实施的版本。

交付物：

- `report.pdf`
- `report.json`
- `manifest.json`

能力：

- PDF 与现有正式报告使用同一份报告文档模型生成。
- PDF 展示报告编号、生成时间、作品摘要、版权记录、验证结论、时间材料、版本链和边界说明。
- JSON 保留完整结构化字段。
- Manifest 固化三个文件的 SHA-256 和生成关系。
- PDF 页脚显示报告编号、页码、生成版本和短摘要。

对外口径：

> 由 HiddenShield 生成的版权证据技术报告，可用于版权管理、平台申诉和争议处理材料整理。

### L2：可独立校验的签名证据包

在 L1 稳定后推进。

新增交付物：

- `manifest.sig` 或等价签名对象
- `verification.txt` / `verification.json`
- 可选 TSA token、registry receipt 等附件

能力：

- Manifest 使用受控签名密钥签名。
- 报告内二维码指向官方只读校验页，或编码离线校验所需的最小信息。
- 校验页只显示报告是否匹配、签发状态、撤销状态和必要摘要，不泄漏原始媒体或本地路径。
- 支持离线 CLI / 桌面端“校验报告包”。
- 支持报告撤销、重签发和版本链。

对外口径：

> 报告包支持完整性校验，可识别报告或附件是否与签发记录一致。

### L3：司法协作证据包

必须在法务、密钥托管、第三方服务和真实案件流程验收后推进。

候选能力：

- 符合长期验证需求的 PDF 数字签名与时间戳。
- 与合规电子认证服务、可信时间服务、公证或司法鉴定合作方衔接。
- 固化操作主体、设备、日志、保全策略和审计链。
- 提供律师版证据目录、证据说明、校验说明和质证问答材料。
- 针对具体案件生成案件级封面、证据编号和附件目录。

限制：

- 不能仅凭 UI、二维码、区块链字样或自签名证书宣称达到司法鉴定效力。
- 是否被法院采纳取决于具体案件、提交方式、证据来源、质证情况和审查结论。

## 4. 报告产品分型

### 4.1 单份版权详细报告

适用：

- 日常版权归档
- 平台原创申诉
- 商务合作前的权属材料整理

建议页数：6 到 10 页。

内容：

- 单个作品与单条版权记录
- 系统验证结论
- 用户权利声明
- 技术字段摘要
- 附件与校验说明

### 4.2 维权证据包

适用：

- 已发现疑似侵权
- 律师咨询、调解、仲裁或诉讼前材料整理

建议页数：10 到 20 页，不含附件。

在单份版权详细报告基础上增加：

- 案件信息与争议对象
- 证据目录
- 原作品、保护记录、疑似侵权材料的对应关系
- 比对结论与比对方法
- 取证来源、时间、操作人和环境说明
- 每项附件的 SHA-256 与获取方式
- 风险、缺失项和需人工补充项

注意：当前实现尚没有完整案件采集、网页取证、侵权样本保全和比对链路，因此维权证据包 PDF 应分阶段开放，不能只将现有单记录报告换封面后冒充案件证据包。

### 4.3 批量版权清单

适用：

- Creator 批量归档
- Studio 团队月度版权资产盘点

建议形态：

- 2 到 4 页总览
- 后接记录表格或独立 CSV / JSON 附件

它不应复制每条完整报告，而应展示资产数量、媒体类型、验证状态、时间范围、异常项和记录摘要。

## 5. PDF 信息架构

### 第 1 页：封面与报告身份

必须展示：

- HiddenShield 品牌标识
- 报告名称
- 报告编号
- 报告类型
- 作品名称
- 权利声明主体
- 报告生成时间与时区
- 状态徽标：`验证通过`、`部分材料缺失`、`验证未通过`
- 二维码或短校验码
- 明确的小字边界说明

封面不应展示大量技术字段。它的任务是建立报告身份和可信感。

### 第 2 页：执行摘要

用一页回答六个问题：

1. 这是什么作品？
2. 谁声明拥有或管理相关权利？
3. HiddenShield 记录了什么？
4. 当前验证结论是什么？
5. 有哪些可信时间或第三方收据？
6. 哪些结论不能由本报告证明？

建议使用“结论卡 + 风险卡”，避免只显示绿色通过。

### 第 3 页：作品与主体信息

字段分组：

- 作品基本信息
- 媒体类型、尺寸、时长
- 创作者显示名
- 作品来源声明
- 创作方式声明
- 人工编辑程度声明
- 训练许可声明
- 自定义权利声明

所有声明字段必须标记为“用户声明”，不能与系统计算结果使用相同视觉标签。

### 第 4 页：版权记录与版本链

展示：

- 版权编号 / watermark UID
- 记录 ID
- 创建时间
- 版本号
- 父版权编号
- 改写原因
- 编号签发模式
- registry 状态与 receipt

视觉建议使用纵向时间轴表达“初始记录 -> 改写 -> 当前版本”，让非技术用户看懂版本关系。

### 第 5 页：媒体完整性与保护副本

展示：

- 原始文件名
- 原始文件 SHA-256
- 保护副本名称
- 保护副本 SHA-256
- 输出策略
- 报告是否包含媒体文件
- 本地路径明确不导出

长摘要采用：

- 前 12 位 + 后 12 位的可读短摘要
- 完整摘要独占等宽字体行
- 可复制文本保留在 PDF 中

### 第 6 页：水印与写后验证

展示：

- Payload 协议版本与字节数
- 媒体载荷角色
- 写入状态
- 写后读取验证状态
- 验证时间
- 验证消息
- payload auth 状态

如果存在失败或缺失，报告必须显示实际状态，不允许通过视觉弱化隐藏。

正式水印事实必须继续来自 `watermark-core` 或其正式端包装层。PDF 生成器只能消费正式报告模型，不得重新计算版权编号、payload、写入或验证结论。

### 第 7 页：可信时间与第三方材料

按来源分层：

- 本机记录时间
- 网络时间
- RFC 3161 TSA
- 云端 registry receipt
- L2 视频存证 receipt
- 其他第三方签名材料

每个来源显示来源名称、时间值、是否存在原始 token / receipt、校验状态和附件编号。

不能把“字段存在”自动显示成“可信”。例如只有网络时间字符串而无可验证 token 时，应显示“补充时间信息”而非“可信时间戳已验证”。

### 第 8 页：视频专项材料

只在存在视频字段时生成。

L1：

- 视频音轨水印事实

L2：

- notary ID
- fingerprint root
- bundle SHA-256
- scene count
- frame sample policy
- receipt signature

L3：

- 仅在当前真实能力边界允许的情况下展示
- 必须显示任务状态、策略摘要、自检置信度、阈值、检查帧数、媒体摘要和 receipt 摘要
- release gate / 内部测试材料不能包装成已售司法能力

### 第 9 页：证据链与生成过程

用流程图表达：

`媒体输入 -> 摘要计算 -> 水印写入 -> 写后读取 -> 版权库记录 -> 时间/收据 -> 报告生成 -> Manifest`

同时列出：

- 应用版本
- 报告 schema 版本
- 报告模板版本
- 生成端
- 生成时间
- 核心协议版本
- 关键验证步骤及状态

建议新增稳定的 `evidenceEvents`，每个事件包含：

- `eventId`
- `eventType`
- `occurredAt`
- `actorType`
- `source`
- `inputDigest`
- `outputDigest`
- `status`
- `receiptRef`

首版可先由现有字段投影生成，后续再演进为真实事件链。

### 第 10 页：结论、限制与使用说明

分成三栏：

- **系统已验证**
- **用户声明**
- **本报告不证明**

固定声明建议：

> 本报告由 HiddenShield 根据版权库记录及其关联技术材料自动生成，用于版权管理、平台申诉和争议处理材料整理。本报告不构成法律意见、司法鉴定意见、公证文书或诉讼结果承诺。报告所载用户声明由声明人负责；技术结论应结合原始电子数据、附件、校验结果和具体案件事实审查。

## 6. 视觉设计方向

### 6.1 关键词

- 克制
- 权威
- 可核验
- 档案感
- 技术中立
- 高可读性

### 6.2 不建议的方向

- 大面积赛博渐变、霓虹蓝紫和发光效果
- 模仿法院徽章、公章、红头文件或司法机关文书
- 使用“区块链已认证”“司法有效”等未经能力边界支持的印章
- 满页密集表格
- 大量绿色勾选制造“全部合法”的错觉

### 6.3 推荐视觉语言

- **纸张**：A4 纵向，正文留足装订与打印边距。
- **主色**：深海军蓝或炭黑，建立档案与技术报告感。
- **辅助色**：低饱和铜金，用于报告编号、章节编号和关键分隔线。
- **状态色**：深绿表示已验证，琥珀表示材料不完整，深红表示验证失败，灰色表示不适用。
- **背景**：暖白，不使用纯灰大底。
- **分隔**：细线、编号、留白优先，不依赖重阴影卡片。
- **字体**：中文优先使用可嵌入的开源黑体正文；标题可使用同家族中黑；摘要和编号使用等宽字体。
- **页眉**：报告简称、作品简称。
- **页脚**：报告编号、模板版本、页码、短摘要。

建议色板：

- 主文字：`#17202A`
- 主品牌：`#17324D`
- 铜金强调：`#9A6B2F`
- 验证通过：`#246B4A`
- 待补材料：`#9A6700`
- 验证失败：`#9B2C2C`
- 次级文字：`#66717E`
- 纸张背景：`#FBFAF7`
- 分隔线：`#D8D3C8`

## 7. 报告状态模型

不要只使用“成功 / 失败”。建议报告顶层增加：

- `verified_complete`：关键材料齐全且验证通过
- `verified_with_gaps`：核心验证通过，但 TSA、registry 或附件存在缺失
- `verification_failed`：关键摘要、payload 或收据验证失败
- `declaration_only`：只有用户声明，没有足够系统验证材料
- `not_applicable`：当前媒体类型或记录不适用某项验证

并生成：

- `overallStatus`
- `statusReasons[]`
- `missingEvidence[]`
- `failedChecks[]`
- `recommendedActions[]`

这组字段会直接提升报告在争议场景中的诚实度和可解释性。

## 8. 数据模型升级建议

现有 `FormalReportDocument` 可演进为 schema v2，新增：

- `templateVersion`
- `generator`
- `subject`
- `work`
- `overallAssessment`
- `evidenceEvents`
- `attachments`
- `integrity`
- `verificationInstructions`
- `legalBoundary`

`integrity` 建议包含：

- `documentJsonSha256`
- `pdfSha256`
- `manifestSha256`
- `signatureAlgorithm`
- `signatureStatus`
- `timestampStatus`

避免 PDF 与 JSON 各自拼装字段。推荐链路：

`VaultRecord -> FormalReportDocument -> PDF renderer / JSON serializer / Manifest builder`

所有输出必须来自同一个不可变报告模型快照。

## 9. 技术实现路线

### 9.1 渲染技术选型原则

优先满足：

- Windows 桌面稳定运行
- 中文字体可嵌入
- A4 分页可控
- 表格跨页、页眉页脚和目录稳定
- 输出可复现
- 不依赖用户机器安装 Office 或浏览器
- 可在 CI 中做结构和视觉回归

建议先做两个技术 spike：

#### 方案 A：HTML/CSS -> PDF

优点：

- 设计效率高
- 复杂排版和打印样式成熟
- 容易制作报告预览

风险：

- Chromium 运行时体积
- 字体与分页跨环境差异
- 需要锁定渲染版本

#### 方案 B：Rust 原生 PDF

优点：

- 依赖边界清晰
- 可完全本地生成
- 输出可控

风险：

- 中文字体、表格、分页和可访问性实现成本高
- 设计迭代速度慢

推荐：先以真实报告 fixture 做 3 天 spike，用“分页稳定性、中文字体、包体积、生成耗时、签名扩展能力、CI 可测性”打分后决定，不在规划阶段直接绑定库。

### 9.2 导出目录建议

```text
HSR-<report-id>/
  report.pdf
  report.json
  manifest.json
  attachments/
    tsa-token.tsr
    registry-receipt.json
    video-notary-receipt.json
  verification/
    README.txt
    verification.json
```

单击下载可以交付 ZIP，但本地导出目录应保留原始文件结构。

### 9.3 PDF/A 与数字签名

- L1 先验证字体嵌入、打印、复制文本和跨阅读器兼容性。
- L2 再评估 PDF/A-2 或 PDF/A-3 归档格式。
- 如将 JSON / Manifest 嵌入 PDF，必须同时保留外部附件，避免接收方无法提取。
- 数字签名必须有明确证书主体、密钥托管、轮换、撤销和长期验证策略。
- 自签名只可用于内部技术验证，不得包装为可信电子签名。

## 10. 桌面与移动端一致性

报告 schema、字段解释、状态模型、免责声明和模板版本必须双端一致。

建议职责：

- **共享合同**：统一 JSON schema、字段字典、fixture 和 golden assertions。
- **桌面端**：首版承担完整 PDF 与证据包生成。
- **移动端**：首版可请求同一云端签发服务，或导出同 schema 的 PDF；不能长期保留“移动端草稿、桌面端正式报告”的产品分裂。
- **云端签发**：只负责报告快照、签名、时间戳、校验与分发，不重新实现水印算法。

如果首版只能桌面生成 PDF：

- 移动端入口必须明确“在桌面端生成完整 PDF”，并保留相同记录字段和报告状态预览。
- 必须在 `docs/双端能力一致性Roadmap.md` 记录限制、fallback 和消除时间点。

## 11. 安全、隐私与防伪

- 默认不包含原始媒体、保护副本、本地路径、对象存储内部地址或下载 token。
- 报告生成前提供字段预览和隐私检查。
- 二维码只携带报告编号、校验地址或短摘要，不携带敏感权利声明全文。
- 在线校验页需要防枚举、访问频控和最小信息披露。
- 报告重新签发必须生成新版本，不覆盖旧报告。
- 撤销不删除历史事实，只标记撤销原因、时间和替代报告。
- Manifest 必须覆盖附件路径、大小和摘要，防止附件替换。

## 12. QA 与发布门禁

### 合同测试

- PDF、JSON、Manifest 来自同一报告模型。
- 双端字段与状态映射一致。
- 不泄漏本地媒体路径、对象存储地址和 token。
- L3 内部字段不会被错误包装成用户可售能力。

- 图片、音频、L1、L2、L3 gate 记录分别有 fixture。
- 无 TSA、无 registry、验证失败、改写版本链等缺失和异常场景均有 fixture。
- 用户声明与系统验证在文案和视觉上明确分离。

### PDF 结构测试

- 文件头、页数、字体嵌入、文本可提取。
- 页眉页脚、页码、报告编号一致。

- 固定 fixture 渲染每页图片。
- 对封面、摘要、版本链、视频页和限制页做截图回归。
- Windows 100%、125%、150% 显示比例不影响最终 PDF。

### 性能目标

首版建议目标：

- 单记录 10 页以内报告，普通桌面设备 3 秒内生成。
- 生成失败不写入成功 usage ledger。
- 临时文件失败后可清理。
- 同一报告模型和模板版本生成的内容字段一致。

## 15. 关键风险

### 风险 1：视觉像法律文书，能力却只是技术报告

- 区分本机时间、网络时间、TSA token 和已验证时间戳。
