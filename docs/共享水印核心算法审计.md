# HiddenShield 共享水印核心算法审计

审计日期：2026-06-20

本文档用于在执行 `docs/共享水印核心与跨端互验推进计划.md` Phase I 前，先梳理当前桌面端、移动端和后端相关能力的算法路径、漂移风险和一次成功门槛。

## 1. 审计结论

当前项目已经具备共享核心基础：`watermark-core` 同时被桌面端 Tauri 和原生移动端 Rust bridge 调用。

但是，不能直接推进迁移或大改。原因是当前“同核”只覆盖核心写入/读取函数，仍有多处会影响最终互验结果的封装层逻辑：

- payload 输入在桌面端和移动端分别构造。
- 移动端图片和音频 payload seed 构造存在重复实现。
- 桌面端音频写入与桌面端音频验证使用不同的音频抽取策略。
- 移动端 Web 预览完全不调用 `watermark-core`，使用 preview marker。
- 视频相关能力当前不是画面盲水印同核能力，而是 L2 指纹存证和桌面端视频音轨写入路径。

Phase I 可以推进，但必须先做契约固化和金样本互验，不能先改算法实现。

## 2. 当前共享核心

核心 crate：

- `watermark-core/src/payload.rs`
- `watermark-core/src/service.rs`
- `watermark-core/src/image.rs`
- `watermark-core/src/audio.rs`
- `watermark-core/src/error.rs`

### 2.1 Payload

正式 payload 长度：32 bytes。

字段：

| 字段 | 长度 | 来源 / 含义 |
| --- | --- | --- |
| magic | 4 bytes | 固定 `HD5H` |
| user_seed | 8 bytes | 用户 / 创作者种子 |
| timestamp | 8 bytes | 写入时间戳，大端 |
| device_id | 4 bytes | 设备标识 |
| ai_flags | 2 bytes | AI 内容声明压缩字段 |
| file_hash | 2 bytes | 文件哈希前缀 |
| auth_tag | 4 bytes | HMAC-SHA256 前 4 字节 |

版权编号规则：

```text
HS-{user_seed[0..2]}-{user_seed[2..4]}-{device_id[0..2]}
```

风险：

- 版权编号规则目前在 `WatermarkPayload::watermark_uid()` 中是正式规则。
- 移动端 Web 预览也手写了相似的 HS 编号格式，但不是正式规则来源。
- 任何平台不应再手写正式版权编号规则。

### 2.2 图片算法

入口：

- `WatermarkService::embed(MediaInput::ImageBytes, ...)`
- `WatermarkService::extract(MediaInput::ImageBytes)`

核心特征：

- DWT / DCT / SVD 写入。
- 支持 `Forensic` 和 `Balanced` 两档强度。
- 默认输出格式由 `EmbedOptions.image_output_format` 决定。
- 默认写入会先调用已有水印拒绝逻辑。
- 读取包含 orientation、padding、brightness、scale、sync packet、dense payload 等恢复候选。

风险：

- 桌面端图片当前统一输出 PNG。
- 移动端原生当前也输出 PNG。
- `watermark-core` 本身支持 JPEG/WebP/BMP/TIFF，但双端产品口径需要明确哪些是正式输出策略。

### 2.3 音频算法

入口：

- `WatermarkService::embed(MediaInput::AudioWavBytes, ...)`
- `WatermarkService::extract(MediaInput::AudioWavBytes)`

核心特征：

- WAV PCM 输入。
- 频域 relative pair 写入。
- marker packet 和 recovery packet 辅助恢复。
- 30 秒最短保护规则对 standalone audio 生效。
- `AudioProtectionMode::VideoTrack` 可跳过 standalone audio 的 30 秒限制，用于视频音轨。
- 读取会按源采样率提取，非 44.1kHz 失败时尝试 canonical fallback。

风险：

- 核心算法接收 WAV，媒体容器解码属于平台封装层。
- 桌面端使用 FFmpeg，移动端使用 Symphonia，两者解码细节不同。
- 因此音频跨端互验必须覆盖不同采样率、声道数和常见容器。

### 2.4 错误类型

当前核心错误：

- `EmbedFailed(String)`
- `ExtractFailed(String)`
- `AlreadyWatermarked { existing_uid }`

风险：

- 错误码仍然偏字符串，不足以作为长期跨端契约。
- 用户可见文案已经在外层翻译，但 Phase I 应固化“核心错误码 -> 平台错误 -> 用户文案”的映射。

## 3. 桌面端算法路径

### 3.1 图片写入

路径：

- `src-tauri/src/pipeline/scheduler.rs`
- `run_image_pipeline`
- `WatermarkPayload::new`
- `WatermarkService::embed(MediaInput::ImageBytes, ...)`
- `verify_embedded_bytes`
- 入库 `VaultRecord`

前后处理：

- 从本机身份读取 `user_seed` 和 `device_id`。
- `timestamp` 使用系统时间纳秒转 `u64`。
- `file_hash` 来自原文件 SHA-256 前 2 字节。
- 图片保护副本统一输出 PNG。
- 写入后用 `WatermarkService::extract` 回读验证。

风险：

- payload 构造在 pipeline 内部完成，而不是一个共享 payload builder。
- 图片输出策略写在桌面 pipeline，不在核心契约中表达。

### 3.2 音频写入

路径：

- `run_audio_pipeline`
- FFprobe 读取时长、采样率、声道。
- FFmpeg 抽取为 PCM WAV，尽量保留源采样率和声道。
- `WatermarkPayload::new`
- `WatermarkService::embed(MediaInput::AudioWavBytes, ...)`
- 写出 `_watermarked.wav`
- `verify_embedded_bytes`

前后处理：

- 30 秒规则在桌面 pipeline 先做一层硬阻断。
- 核心 standalone audio 也会再做最短时长校验。
- 非 WAV 源由 FFmpeg 转为 WAV。

风险：

- FFmpeg 抽取策略影响最终水印稳定性。
- 与移动端 Symphonia 解码不完全等价，需要金样本验证。

### 3.3 桌面端验证

路径：

- `src-tauri/src/commands/verify.rs`
- 图片：直接读 bytes 后 `WatermarkService::extract(MediaInput::ImageBytes)`
- 音频/视频：FFmpeg 抽音频到 WAV 后 `WatermarkService::extract(MediaInput::AudioWavBytes)`

风险：

- 验证音频时仍强制 `-ar 44100 -ac 2`。
- 写入音频时已经尽量保留源采样率和声道。
- 这不一定导致失败，因为 core 有采样率 fallback，但它是跨端互验高风险点。

## 4. 原生移动端算法路径

### 4.1 Flutter bridge

路径：

- `mobile_app/lib/bridge/rust_watermark_bridge.dart`
- 图片调用 `embedImageForMobile` / `extractImageForMobile`
- 音频调用 `embedAudioWavForMobile` / `extractAudioWavForMobile`

行为：

- 写入后 Flutter bridge 会再次 read 产物，确认版权编号一致。
- 图片输出 PNG。
- 音频输出 WAV。

风险：

- Flutter 层仍构造 `WatermarkPayloadSeed`。
- 写入后验证在 Flutter bridge 做，核心只负责读写。

### 4.2 Mobile Rust bridge

路径：

- `mobile_app/rust/src/api.rs`
- `MobileMediaPayload::into_core_payload`
- `WatermarkPayload::new`
- `WatermarkService::embed/extract`

图片：

- 输入 bytes 直接交给 core。
- 支持 `Png/Jpeg/WebP` 输出枚举，但 Flutter 当前传 PNG。

音频：

- WAV 直接使用。
- 非 WAV 用 Symphonia 解码为 interleaved PCM，再写成 16-bit WAV。
- 保留 source sample rate 和 decoded channel count。

风险：

- AI flags 在移动端 bridge 默认使用 `default_ai_flags()`，不像桌面端可从选项传入。
- 音频解码器与桌面 FFmpeg 不同。
- 目前已有 mobile crate 内的“移动产物可被 desktop core 提取”测试，但缺少仓库级双向金样本门禁。

### 4.3 Payload seed

图片页面：

- `mobile_app/lib/features/workspace/watermark_payload_seed.dart`

音频页面：

- `mobile_app/lib/features/workspace/audio_embed_page.dart` 内部重复 `_buildPayloadSeed`

当前逻辑：

- `user_seed` = creator label SHA-256 前 8 bytes。
- `device_id` = creator label SHA-256 第 8 到 12 bytes。
- `file_hash` = 输入 bytes SHA-256 前 2 bytes。
- `timestamp` = 秒级时间戳。

风险：

- 音频和图片 payload seed 重复实现，未来极易漂移。
- 桌面端身份来源是本机 identity bytes，移动端是 creator label hash，两端写入同一创作者时未必生成同一 user_seed/device_id。
- 这不影响“另一端可解析”，但会影响版权编号策略、创作者身份一致性和跨端账号语义。

## 5. 移动端 Web 预览路径

路径：

- `mobile_app/lib/bridge/local_preview_watermark_bridge.dart`

行为：

- 不调用 `watermark-core`。
- 在原 bytes 尾部追加 `HS_PREVIEW_WM:<uid>` marker。
- 使用 `_previewHash` 和手写 HS 编号格式。
- `supportsProductionWatermark => false`。

审计结论：

- Web 预览不是正式水印能力。
- Web 预览生成物不能被用于桌面端/移动端互验。
- Web 预览不能进入正式版权库、正式报告或云同步 payload。

Phase I 之前不能把 Web 预览重新打开为“正式写入/验证”，除非先接入 WASM 同核。

## 6. 后端与视频受影响面

### 6.1 后端

当前 feedback backend 主要负责：

- 账户 / 权益。
- 匿名反馈。
- 可信时间代理。
- 云同步相关接口。
- L2 视频指纹存证 API：`POST /v1/video-fingerprints/notaries`。

审计结论：

- 当前后端不直接执行图片/音频本地水印算法。
- 当前后端已经参与 L2 视频指纹存证闭环，会校验 notary request、upload manifest、crop windows 和 usage ledger。
- Phase I 改动如果局限于 `watermark-core` API、客户端 wrapper 和契约测试，对后端图片/音频业务接口影响较小。
- 但 L2 / L3 视频能力必须纳入 Phase I 的跨端一致性规划，不能只按“未来视频”占位处理。

### 6.2 视频

当前视频相关能力必须拆成三类审计，不能混为一谈。

#### L1：视频音轨水印

现状：

- 桌面端视频 pipeline 会抽取视频音轨，调用 `WatermarkService::embed(MediaInput::AudioWavBytes, ...)` 写入音频水印，再用 FFmpeg 合成目标平台视频。
- 该能力复用 `watermark-core` 的音频算法，属于“视频容器中的音频水印”。
- 移动端本地不做视频写入。

一致性要求：

- 桌面端写入的视频成品，桌面端和未来支持视频验证的端都必须通过抽音频读取到同一 `watermark_uid`。
- 移动端如果只支持只读验证，必须明确是“抽取视频音轨验证音频水印”，不能表述成画面盲水印。
- L1 不上传原始视频、加水印视频或本地路径。

风险：

- 桌面视频 pipeline 使用 `AudioProtectionMode::VideoTrack`，会绕过 standalone audio 的 30 秒规则，这是合理的，但必须进入契约说明。
- 视频验证路径如果强制重采样，可能影响低码率或特殊声道视频的音轨水印提取。

#### L2：视频画面指纹存证

现状：

- `src-tauri/src/video_fingerprint.rs` 已能从本地视频生成不可逆 `VideoFingerprintBundle`。
- Bundle 包含整帧摘要、局部块摘要、裁剪候选窗口摘要、`client_signature`。
- `src-tauri/src/sync/cloud.rs` 已提供 `video_fingerprint_bundle_to_notary_request`，将 bundle 映射为 notary request。
- `feedback-backend` 已提供 `/v1/video-fingerprints/notaries`，拒绝原始视频、加水印视频、本地路径，并要求 `crop_window_fingerprint_root`。
- 桌面端支持生成 bundle、提交存证、保存版权库记录。
- 移动端支持通过云同步查看 L2 视频存证记录和报告草稿字段。

一致性要求：

- L2 不是 `watermark-core` 水印算法，也不是视频画面盲水印；它是不可逆指纹存证与相似性证据增强。
- 桌面端生成并提交的 L2 notary record，移动端必须能完整展示同一组字段：存证编号、存证时间、收据签名、usage ledger、指纹根、bundle 摘要、bundle 大小、采样帧、生成耗时、采样策略。
- L2 云同步 payload 不得包含原始视频、加水印视频、本地 bundle 路径或本地文件路径。
- L2 合同必须继续要求三层摘要，不能退回只保存整帧 root。

风险：

- `video_fingerprint.rs` 与 `video_fingerprint_spike.rs` 存在相似但独立的指纹逻辑，后续需要确保生产生成器和 spike/contract 的字段语义不漂移。
- `watermark_uid` 当前为 `l2-{source_hash_prefix}`，与图片/音频 `HS-...` 版权编号不是同一规则。产品和报告必须明确 L2 是存证编号/指纹记录，不是盲水印 UID。
- 移动端当前只读展示 L2，如果后续增加移动端生成 bundle，必须复用同一生成器或共享服务，并补跨端 bundle fixture。

#### L3：端云协同视频画面盲水印

现状：

- 已在商业化文档中设计为未来高阶能力。
- 当前没有正式画面盲水印算法实现。
- `cloud_video_processing` 控制的是未来 L3 能力，不控制 L2。

一致性要求：

- L3 进入实现前，必须先完成 `watermark-core` 视频画面盲水印算法设计和云端执行包装设计。
- 桌面端、移动端、后端和云任务不得各自实现不同的视频画面水印算法。
- 云端可以负责策略包、密钥边界、任务调度和自检编排，但盲水印写入/验证算法仍必须来自 `watermark-core`。
- L3 必须有策略包、防逆向、密钥边界、客户端自检、云端验证和失败不扣费契约。
- L3 的跨端互验至少包括：桌面渲染/云端验证、云端策略/桌面自检、未来移动端只读验证或提交验证样本。

风险：

- 商业化 Roadmap 中 L3 不能直接复用当前 L2 指纹存证概念。
- L2 相似性证据不能替代 L3 画面盲水印命中。
- 移动端不应单独实现一套视频画面水印算法。

## 7. Phase I 任务审计

### Phase I-1：核心契约固化

结论：必须先做。

范围：

- 不改算法。
- 文档化并测试锁定 payload、版权编号、错误码、Image/Audio options。
- 抽出平台共享的 payload builder 设计。

成功门槛：

- 知道哪些字段来自账户身份，哪些来自文件，哪些来自写入选项。
- 明确桌面端和移动端版权编号一致性的产品含义。

### Phase I-2：跨端金样本 fixtures

结论：必须做，但不能手工依赖桌面 UI 或 Flutter UI。

建议：

- 使用 Rust 层直接生成 fixtures。
- 用桌面依赖的 `watermark-core` 路径和移动 Rust bridge 路径互读。
- 音频至少覆盖 WAV、非 WAV 归一化、单声道、双声道、22.05kHz/44.1kHz。

成功门槛：

- 测试失败时能看出是 payload、媒体预处理、核心算法还是 wrapper 问题。

### Phase I-3：发布门禁接入

结论：在 fixtures 稳定后做。

风险：

- 如果过早接 CI，可能把现有不稳定样本变成噪声。
- 需要先确定哪些矩阵是 release-blocking，哪些是 observation。

成功门槛：

- `npm run dual:contract` 或新命令能明确报告跨端互验结果。

### Phase I-4：Web 预览边界收口

结论：必须保持保守。

建议：

- 当前 Web 预览继续不能代表正式能力。
- 如果业务需要 Web 预览可写可验，必须走 WASM 同核方案。
- Web 预览 bridge 的结果必须携带非正式标记，状态层不能只依赖页面按钮禁用来隔离正式记录。
- 非正式预览结果不得进入正式版权库、云同步队列、正式报告或跨端互验证据。

成功门槛：

- 用户不会误以为 Web 预览生成的是桌面可验证的正式保护副本。

### Phase I-5：保护副本出口

结论：排在同核互验之后。

原因：

- 如果先做保存/分享入口，用户拿到的文件仍可能无法跨端验证。
- 产品价值取决于同核产物可被另一端解析。

成功门槛：

- 原生移动端生成的保护副本可以被桌面端验证后，再开放导出体验为正式验收路径。
- 单文件出口必须基于正式 `watermark-core` 写入结果 bytes，不通过 Web preview marker、不伪造本地路径。
- 保存 / 分享动作只交给系统面板处理，不把保护副本路径、媒体路径或临时文件路径写入云同步。

### Phase I-6：视频同核设计

结论：必须纳入 Phase I，但要按 L1 / L2 / L3 分层推进，不能提前编码 L3。

成功门槛：

- 明确视频画面盲水印、视频音轨水印、L2 视频指纹存证三者边界。
- 明确本地/云端处理和商业化权益。
- L1 明确复用 `watermark-core` 音频算法，并补视频音轨写入/抽取验证互验要求。
- L2 明确复用现有 `VideoFingerprintBundle` / notary request / cloud receipt 契约，并补桌面生成、后端存证、移动端展示的双端一致性要求。
- L3 在写代码前必须先完成 `watermark-core` 视频画面算法、云端执行包装、策略包和客户端自检协议设计。

## 8. 一次成功门槛

Phase I 进入实现前必须满足：

- 不改核心算法，只固化契约和互验。
- 所有正式盲水印路径都能被映射到 `watermark-core`，云端路径也只能是 `watermark-core` 的部署/调度包装。
- Web 预览明确排除在正式互验之外。
- 音频转码差异被列为互验矩阵，不靠推测判断。
- payload 构造规则有单一设计，不再散落在 UI 页面里。
- 错误码有核心层、平台层、用户层三段映射。
- CI 只接入稳定、可复现、能定位原因的互验用例。

## 9. 主要风险清单

| 风险 | 等级 | 说明 | 建议 |
| --- | --- | --- | --- |
| payload 构造漂移 | P0 | 桌面端用 identity bytes，移动端用 creator label hash | 先设计共享 payload builder 契约 |
| 音频预处理漂移 | P0 | 桌面 FFmpeg 与移动 Symphonia 解码不同 | 金样本覆盖采样率、声道、容器 |
| Web 预览误当正式能力 | P0 | preview marker 无法被桌面 core 解析 | 保持正式禁用或接 WASM 同核 |
| 错误码字符串化 | P1 | 核心错误不够结构化 | Phase I-1 增加错误码契约 |
| 视频概念混淆 | P0 | L1 音轨水印、L2 指纹存证、L3 画面盲水印不是同一能力 | Phase I 视频规划必须分层写清互验要求 |
| 核心外算法分叉 | P0 | 未来可能在 Tauri、Flutter、后端、云任务或脚本中另写盲水印注入/验证算法 | 增加架构契约门禁，盲水印算法只能出现在 `watermark-core` |
| L2 指纹逻辑漂移 | P1 | 生产生成器、spike 工具和 bundle verifier 可能字段语义漂移 | 将 L2 bundle fixture 和 cloud-video 合同纳入 Phase I 视频门禁 |
| 移动端 AI flags 缺失 | P1 | 移动端默认 flags，桌面端支持选项 | 先纳入 payload 契约，后续补 UI |

## 10. 推荐下一步

先执行 Phase I-1 的“契约审计落地”，不要直接迁移算法：

1. 在 `watermark-core` 增加/整理契约测试，锁定 payload 编码、版权编号、错误类型、图片/音频 options。
2. 设计共享 payload builder，把桌面端 identity 与移动端 creator profile 的输入关系写清。
3. 设计跨端 fixtures 矩阵，明确 release-blocking 与 observation 项。
4. 之后再实现 Phase I-2 的金样本互验。
